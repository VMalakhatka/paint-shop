# PC WayForPay Checkbox

## 0.2.0: независимый банковский приход ФОЛИО

Добавлен отдельный consumer подтверждённой оплаты: `FolioPayments`, `FolioStore`,
`FolioCommand`, `FolioClient`. Приход на складе 5 не зависит от состояния Checkbox
или счетов; привязка плательщика сохраняется при первом Approved. Распределение
по счетам выполняется отдельно. Возврат сохраняет приход и требует проверки расхода.
Java владеет native INSERT_PLAT и атомарным MSSQL-журналом; WordPress — durable outbox.
Новые настройки выключены по умолчанию. Точный запуск, миграции, статусы и ограничения:
[FOLIO_WFP_PAYMENTS.md](../../../docs/FOLIO_WFP_PAYMENTS.md).
Проверки: `php tests/folio-payments.php`, также с аргументами `preview` и `off`;
существующие `flow.php`, `return-page.php`, локальная миграция и `local-locks.php`.
Production автоматический поток ещё не включён.

Владелец: интеграция оплат Lavka/WooCommerce. Ниже — контракт чека из версии 0.1.1.
Новый адаптер **подтверждённая оплата WayForPay → команда → универсальный
`pc-checkbox-fiscalization` → чек**. Исполнитель Checkbox не выбирает заказы.
Последующая production-проверка 2026-10-16 подтвердила один live-чек; границы
внешней приёмки перечислены в [WayForPay runbook](../../../docs/WAYFORPAY_TEST_ACCESS.md).

## Контракт и границы

- Для установленного gateway `wayforpay` (legacy 1.0): перехватывает
  `woocommerce_api_wc_wayforpay` на priority `-100`. URL `?wc-api=WC_wayforpay`
  и платёжная форма шлюза не меняются. Обновления gateway требуют повторной проверки.
- Когда режим включён, обработчик завершает HTTP-ответ и не допускает второй
  обработки vendor-плагином. В `off` управление остаётся vendor-плагину.
- Только подписанный callback `Approved` с `reasonCode=1100`, своим merchant,
  точной суммой, UAH и reference `ORDER_ID_woo_w4p_TIMESTAMP` подтверждает оплату.
  Подпись проверяется по официальному набору полей HMAC-MD5, ответ `accept` подписан.
  Redirect браузера, `processing`, `pending`, `on-hold`, ручная смена статуса — не источник чека.
- Для новых операций нужен заказ, созданный после явного cutoff, ещё не оплаченный,
  со статусом pending/on-hold/failed и способом оплаты wayforpay. Нет backfill старых заказов.
- Команда и UUID сохраняются ДО `payment_complete(reference)`: Folio может затем
  разделить исходный заказ. Проверенный marker `_pc_wfp_verified` содержит reference,
  сумму и валюту. Фискальные повторы не вызывают создание документов ФОЛИО.
  Folio-хуки остаются владельцами своих идемпотентных операций.
- Не переводит заказ принудительно в completed. Вызывается штатный Woo payment_complete.
  После crash сохранённый date_paid предотвращает повтор этого перехода; этот
  checkpoint не гарантирует завершение всех сторонних Woo-хуков — их проверяют отдельно.
- Чек создаётся через Action Scheduler (группа `pc-wfp-checkbox`), не внутри callback.
  Sweep каждые 5 минут восстанавливает потерянную постановку задачи из журнала.

## Данные, суммы и налоги

Берутся оплаченные line totals Woo с налогами, уже после скидок, доставка и
положительные fee. Денежные строки преобразуются в целые копейки, без float-суммирования.
Целое количество при необходимости делится на две цены, различающиеся на копейку:
сумма строк и сумма CASHLESS-платежа обязаны совпасть с подтверждённой оплатой.
SKU берётся из товара; если его нет — устойчивый `woo-item-ID`. Название — из позиции заказа.

Текущая версия поддерживает **одну явно заданную налоговую группу для всех строк**.
Код `8` подтверждён API тестового и выбранного боевого кассира как «Без ПДВ»
(2026-10-16); для другой организации/ассортимента нужна новая проверка.
Смешанные налоговые группы, акцизные реквизиты,
дробное количество, отрицательные fee и распределение ненулевой суммы с нулевой
ценой требуют отдельного mapping. Нулевые строки не включаются. При ошибке mapping
подтверждённая оплата сохраняется, чек получает BLOCKED, фиктивная общая строка не создаётся.
Пустой заблокированный snapshot нельзя исправить кнопкой повтора: нужен отдельный
проверенный процесс восстановления, не новый operation_key вслепую.

Email доставки читается из Woo только в worker. Для первого запроса фиксируется
HMAC адреса; изменение адреса перед повторной отправкой блокирует повтор. В snapshot
email не копируется. Checkbox получает `delivery.email`; фактическая доставка письма
должна быть проверена при внешнем тесте. Ротация WP auth salt требует проверки ожидающих операций.

## Настройки

Только защищённые, исключённые из Git конфиги. Новый плагин не имеет поля для секретов.
Checkbox использует существующие `PC_CHECKBOX_*` из конфигурации исполнителя.
WayForPay по умолчанию использует уже настроенные `merchant_account` / `secret_key`
из `woocommerce_wayforpay_settings`. Можно переопределить их защищёнными константами
`PC_WFP_MERCHANT_ACCOUNT` / `PC_WFP_MERCHANT_SECRET`; значения обязаны совпадать
с merchant, которым подписывает форму gateway. Старые секреты этим изменением не мигрируются.

| Константа | Значение / назначение |
| --- | --- |
| `PC_WFP_CHECKBOX_MODE` | `off` по умолчанию; `preview`, `test`, `live` |
| `PC_WFP_CHECKBOX_START_AT` | Фиксированный ISO-8601 UTC момент начала обработки новых заказов; обязателен |
| `PC_WFP_CHECKBOX_TAX_CODE` | Обязательное целое число; подтверждённая группа кассы |
| `PC_WFP_PRRO_DISABLED_CONFIRMED` | Строго `true` только после проверки, что WayForPay pRRO отключён |
| `PC_WFP_MERCHANT_MODE` | `test` или `live`: проверенный оператором режим merchant, обязателен вне preview |
| `PC_WFP_CHECKBOX_PAUSED` | Строго `true` останавливает фискальные worker, сохраняя проверку callback и оплату |
| `PC_CHECKBOX_ALLOW_FISCALIZATION` | Строго `true` для отправки чека исполнителем |
| `PC_CHECKBOX_ALLOW_LIVE` | Оставить `false` для тестов; боевой режим требует отдельного разрешения |

Allowlist покупателей в Лавке **не доказывает тестовый merchant**. Подписанный callback
не доказывает sandbox-режим WayForPay. Нельзя сочетать реальные оплаты клиентов с
тестовой кассой. Worker сверяет среду кассира и подтверждённый merchant mode с режимом
сохранённой операции. Не переключать существующую очередь test→live.

`preview` сохраняет команду и проверяет её локально без API Checkbox, но настоящий
Approved всё равно подтверждает оплату в Woo. Это не симулятор платежа. PREVIEW не
превращается автоматически в чек; для каждого этапа теста используйте новый заказ.

## Идемпотентность, хранение, ошибки

`{prefix}pc_wfp_receipts`: уникальный order_id и reference, merchant hash, сумма,
валюта, неизменяемая команда, режим, статус, timestamps, attempts, next_run,
payment_applied, refunded. Код операции — merchant hash + Woo order + SELL:v1.
Универсальный исполнитель хранит свой request hash и UUID чека.

Оба уровня используют MySQL advisory locks (разные соединения не могут одновременно
отправлять одну операцию). Сбой сохранения PROCESSING в исполнителе останавливает
отправку. PROCESSING/UNCERTAIN всегда ведут к lookup того же UUID, даже после ручного
повтора. 404 после timeout не разрешает новый POST. Не удалять записи для «повтора».

До 8 автоматических попыток с экспоненциальной задержкой, максимум час между ними.
429/5xx/временные сбои повторяются, неопределённые исходы сверяются. Постоянные ошибки
блокируют обработку. Сменой управляет исполнитель: `require_open` требует ручного
открытия, `open_if_missing` разрешает открытие при исполнении команды.
Адаптер сам сменами не управляет. После лимита менеджер проверяет исход перед возобновлением.

В карточке заказа: статус, режим, код ошибки, число попыток, фискальный номер, UUID
и ссылка на HTML чека. Действие «Reconcile / resume Checkbox receipt» доступно
manage_woocommerce через штатную nonce-защищённую форму Woo. Успешный чек повторно
не создаётся. Просмотр чека содержит персональные данные: не публиковать ссылку.

В 0.1.1 карточка показывает сохранённые stage/HTTP/message/shift ID исполнителя.
BLOCKED сама после deploy не перезапускается. Исправить причину, сверить состояние
чека и вручную возобновить исходную операцию. Фискальный повтор не создаёт документ ФОЛИО.

### Обновление статуса в карточке (0.2.1)

При `QUEUED`/`RECONCILE` старый отказ не показывается как текущая ошибка:
он доступен в свёрнутой «Диагностике предыдущей попытки». `BLOCKED` сохраняет
заметную диагностику. Успех показывает фискальный номер и ссылку, без старой ошибки.
Время изменения сохранённого статуса указано в UTC. Если исполнитель уже подтвердил
чек, а адаптер ещё синхронизируется, показывается подтверждённый чек и пояснение.

Кнопка **Refresh receipt status / Оновити статус чека** только перечитывает
сохранённый статус сайта: она не создаёт чек, не вызывает Checkbox API, не запускает
worker и не изменяет ФОЛИО. Требуются `manage_woocommerce`, право редактировать этот
заказ и nonce конкретного заказа. Работает с HPOS через Woo CRUD.
Открытая карточка обновляет только блок чека каждые 15 секунд, пока состояние
ожидающее (не более 40 автоматических запросов; в скрытой вкладке запросов нет).
При успехе автообновление прекращается; при сетевой ошибке остаётся последний
результат с предупреждением. Ручное обновление доступно и после лимита.
Несохранённые поля заказа и блок банковского прихода не перезагружаются.

Это обновление UI, а не ускорение фоновой очереди: reconciliation может ожидать
пятиминутного recovery sweep и запуска WP-Cron. Повторять продажу из-за задержки
нельзя. Обновите страницу один раз после deploy, чтобы загрузить новый скрипт.
Миграций, новых ключей и повторной активации нет. Rollback — предыдущий каталог
плагина; журналы/очередь не удалять. Локальные проверки: `tests/receipt-panel.php`,
`tests/receipt-status.js`, прежние `tests/flow.php` и `tests/folio-payments.php`.
Production UI требует отдельного deploy и приёмки.

## Возврат покупателя (0.1.1)

Legacy gateway возвращает `?order=…&key=…` на выбранную страницу checkout.
`ReturnPage` проверяет ключ и gateway и переводит на штатную `order-received`.
Сохраняются Woo-проверки владельца/входа/email. Callback `wc-api` и другие gateway
не перенаправляются. Успех требует проверенного marker, совпадения transaction ID
и paid date, включая исходный split-заказ. До callback показывается ожидание;
отмена/возврат не выглядят как успех. Страница не подтверждает оплату и не запускает чек.

Приёмка после deploy: desktop/mobile, гость/вошедший покупатель, callback до/после
возврата, отмена, неверный ключ и split. Production UI ещё не проверен.

Секреты и сырые callback/card данные в журнал не пишутся; команда содержит товарные
строки — защищать БД и backup как бизнес-данные. Удаление/деактивация плагина не
удаляет журнал. Вторая reference для того же заказа возвращает 409 и требует проверки.

`Refunded` блокирует ещё не отправленную продажу, оставляет REFUND_REVIEW и заметку.
Даже refund-before-Approved сохраняет блокирующую запись. Поздний Approved её не
снимает. **Автовозвраты и Woo refund не выполняются**: callback не задаёт надёжный
построчный состав возврата. Уже выданный чек автоматически не аннулируется.

## Развёртывание, приёмка и откат

1. После отдельного разрешения deploy оба плагина (`pc-checkbox-fiscalization`
   и `pc-wayforpay-checkbox`) и переводы. Новый плагин в deploy manifest имеет
   `manual`: активировать отдельно, первоначально MODE=off; проверить таблицу.
2. Проверить Classic Checkout, HPOS, текущий gateway callback, единственного pRRO,
   действительно тестовый merchant, тестового кассира, налог и отсутствие живой очереди.
   Не включать способ оплаты всем клиентам до приёмки.
3. Задать фиксированный cutoff, налог и подтверждения. На отдельном новом тестовом
   заказе выполнить preview, проверить строки/доставку/скидку/сумму; validate через
   API исполнителя с той же подготовленной командой. Preview не использовать для
   реально оплачиваемых клиентских заказов: чек из него сам не появится.
4. После подтверждения preview открыть тестовую смену и выполнить новую тестовую
   оплату в MODE=test при ALLOW_LIVE=false. Дождаться Action Scheduler и SUCCEEDED.
   Сверить сумму/номер/UUID в Checkbox, письмо покупателю, заказ и документы ФОЛИО.
5. Проверить повтор callback, отложенный callback после возврата браузера, отказ,
   очередь после сбоя, один чек/один Folio lifecycle, refund review. Не воспроизводить
   неизвестные реальные платежи; внешние тесты проводить отдельными заказами.
6. Live rollout отдельно: подтверждённые боевые реквизиты и налоги, выключенный
   WayForPay pRRO, пустая или разобранная тестовая очередь, новый cutoff и разрешение
   на малую реальную оплату. Checkout Blocks не заявлены поддержанными legacy gateway.

Аварийная пауза: `PC_WFP_CHECKBOX_PAUSED=true`, оставить плагин включённым — callback
продолжает проверять оплату, задания не расходуют попытки. После разбора убрать паузу.
`MODE=off`/деактивация — полный откат перехвата к legacy gateway; это **не** безопасная
пауза очереди с сохранением новых проверок оплаты. Не удалять журналы и не менять
UUID неизвестных операций. Перед откатом к старой версии исполнителя остановить
адаптер и сверить UNCERTAIN, поскольку старая версия не имеет operation lock.

## Воспроизводимые проверки

Из корня репозитория:

```sh
php wp-content/plugins/pc-wayforpay-checkbox/tests/flow.php
php wp-content/plugins/pc-wayforpay-checkbox/tests/return-page.php
php wp-content/plugins/pc-checkbox-fiscalization/tests/executor-safety.php
php wp-content/plugins/pc-checkbox-fiscalization/tests/api-diagnostics.php
php -d zend.assertions=1 -d assert.exception=1 wp-content/plugins/pc-checkbox-fiscalization/tests/command-validator-smoke.php
wp --skip-plugins --skip-themes eval-file wp-content/plugins/pc-wayforpay-checkbox/tests/local-locks.php
```

Первые тесты используют фиктивные Woo/API/SQL boundaries; последний проверяет
конкуренцию на двух настоящих соединениях только paint.local. Они не являются
доказательством реальной оплаты, доставки письма или записи в ФОЛИО/ДПС.
Внешний E2E остаётся обязательным перед включением production.
