# Настраиваемые транспортные склады для аналитики и закупки

Дата: 2026-09-06. Статус: АРХИВ исходного задания, заменено контрактом v3.
Актуальный источник: Java `docs/api/FOLIO_TRANSIT_WAREHOUSES_FRONTEND.md`;
регламент WordPress: [OPERATIONS_RUNBOOK.md](../OPERATIONS_RUNBOOK.md),
раздел «Глобальные транспортные склады». Ниже сохранены исходные требования,
а не текущее состояние: отправка списка и обработка sources уже подключены
в WordPress через capability-gate. В v3 физический остаток и поставщицкая часть
разделены, а общий итог закупки блокируется до согласованного сетевого снимка.
Деплой и операторская сверка остаются отдельно.
Владелец backend: Java/Folio; WordPress: lavka-sync и lavka-price-sync.

## Что уже сделано в WordPress

- Общая настройка `lavka_transit_warehouse_ids`: уникальные положительные ID,
  отсортированные; отсутствующая option наследует `[9]`, явный `[]` отключает учёт.
- Preview проверяет совпадение настроенного источника и `inTransitStock.warehouseId`.
  Нынешний ответ с одним складом не принимается как сумма нескольких складов.
- Для положительного объёма нужны `CONFIRMED_SUPPLIER_ORIGIN`,
  `supplierOriginConfirmed=true`, неотрицательное `availableForPlanningQuantity`
  и `generationId`. Подтверждённый `NO_IN_TRANSIT_STOCK` означает ноль.
- У одной группы подтверждённый общий объём подставляется автоматически; у нескольких
  групп менеджер распределяет его без превышения общего количества. Неизвестный
  источник нельзя обойти ручным вводом. Пересечение транспорта и групп запрещено.
- Настройка фиксируется в preview и экспорте, её смена требует нового расчёта.

В текущих `FolioProductAnalyticsQueryRequest.Calculation` нет такого параметра;
`InTransitStock` и `TransitCapability` содержат единственный `warehouseId`.
Основание: `FOLIO_PRODUCT_ANALYTICS_FRONTEND_HANDOFF_V4.md`, раздел inTransitStock,
и указанные DTO Java. WordPress пока НЕ передаёт предложенный ниже параметр.

## Предлагаемое расширение существующих endpoint

Новый endpoint не обязателен. Расширить capabilities, query, пагинацию и экспорт
экономической аналитики, сохранив старый запрос совместимым:

```json
{
  "calculation": {
    "transit": {
      "warehouseIds": [9, 10],
      "configurationRevision": "sha256-of-canonical-warehouse-id-list"
    }
  }
}
```

Это пример поля, а не полный запрос. `warehouseIds` аналитического scope остаётся
списком складов спроса; транспорт отдельно и не расширяет продажи/ABC/фильтры
движений. Пустой список означает отключение, отсутствующее поле сохраняет legacy 9.
Список передаёт WordPress server-side из глобальных настроек, не из копии сценария.
Revision сверяется с каноническим списком; окончательное имя поля согласовать.

Capabilities должны явно сообщать поддержку configurable transit, доступность
каждого источника, поколения, причины недоступности и поддерживаемую версию расчёта.
Не ограничиваться общим `ready=true`, если один из источников отсутствует.

## Ответ и расчёт

Возвращать выбранные ID/revision в context, поколения всех транспортных снимков,
для каждого SKU список источников с существующими полями `InTransitStock` и общий
подтверждённый объём. Не суммировать SKU из другой `sourceDatabase`.
Для каждого источника сохранить физический/зарезервированный/доступный остаток,
происхождение от поставщика, статус, предупреждения, поколение/дату снимка.

Суммировать только текущий подтверждённый `availableForPlanningQuantity`, не
`suppliers[].receiptQuantityInHorizon` (это исторические приходы, не текущий остаток).
Не разрешать неизвестные остатки, смешанное происхождение или отрицательные
количества через молчаливое обнуление. Если один источник неизвестен, итоговый
planning quantity должен быть null с явным статусом неполных данных; отдельно
можно вернуть известную часть для диагностики, но не как полный итог.

Товар в пути уменьшает потребность закупки, не прогноз спроса:

```text
закупка = max(0, целевой запас - доступно в группе
              - подтверждённый транзит, выделенный группе
              - другие подтверждённые поступления
              - перемещение в группу + перемещение из группы)
```

Затем применяются MOQ/кратность/лимиты приёмки. Не включать одну партию также в
открытые заказы поставщику. Для будущего автоматического распределения нужны
подтверждённое назначение партии и ETA/доступный горизонт. До их появления
назначение нескольких групп подтверждает менеджер. Нельзя назначить весь общий
остаток каждой группе. Доступный транзит не является донором перемещения со склада.

## Целостность и эксплуатация

- Использовать read-only данные ФОЛІО/ACTIVE snapshots; никаких перерасчётов,
  документов, MIN/MAX, остатков или mode changes ради этого отчёта.
- Транспортные склады обновляются отдельно через snapshot/refresh, последовательно;
  учётная кампания для этого не требуется. Неподдерживаемый режим не менять.
- Все поколения транспортных источников и revision фиксировать в курсоре,
  сверять на каждой странице/экспорте. Смена → явный конфликт, без смешения снимков.
- Дубликаты ID удалить; неизвестный/неподдерживаемый склад показать явно.
- Установить лимит числа источников и исключить N+1 SQL-запросы по каждой SKU.
- Обновить контракт и handoff. Затем WordPress подключит capability-gated передачу
  списка, новый ответ, сортировки/фильтры/экспорт и перестанет использовать legacy guard.

## Приёмка

1. Старый запрос по-прежнему возвращает источник 9.
2. `[9]` даёт тот же результат, что legacy; `[9, 10]` возвращает оба источника.
3. 12 доступных в 9 и 8 в 10 → общий транзит 20, не сумма исторических приходов.
4. Цель 90, доступно 30, транзит 20 → закупка 40 при нулевых других поступлениях
   и упаковке 10; спрос остаётся 90. Для двух групп сумма выделенного транзита ≤20.
5. Резервы, mixed origin, отсутствие снимка и неподтверждённый поставщик
   не создают ложный готовый результат. `[]` явно отключает транзит.
6. Смена транспортного поколения/revision между страницами или перед экспортом
   выявляется как конфликт; CSV и XLSX содержат одинаковый контекст источников.
7. Сверка нескольких рабочих SKU оператором, без изменений Paint_Ua.
