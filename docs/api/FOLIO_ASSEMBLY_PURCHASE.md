# Прогноз компонентов для заказа одному поставщику

Владелец: Java `FolioAssemblyDao` / `FolioAssemblyGraph` — рецепты ФОЛИО;
WordPress `lavka-price-sync/inc/purchase-assembly.php` — распространение потребности,
`purchase-planning-model.php` — существующий групповой прогноз и вычитание запасов.
Подготовлено 2026-10-09. Проверка на локальных fixtures; production ещё не обновлён.

## Область расчёта

В сценарии выбирается ровно один `currentSuppliers INCLUDE`. Исходные товары
остаются корнями расчёта. По действующим рецептам система находит всех потребляющих
их детей и внуков независимо от поставщика, группы и остальных товарных фильтров.
Для этих SKU отдельно запрашивается обычная аналитика с теми же складами, периодом,
фильтрами движений и поколениями снимков. Фильтр наличия снимается. Смена поколения
или неполная пагинация прерывает расчёт; отсутствие ребёнка блокирует его предков.
Уже отобранный ребёнок не загружается повторно (сопоставление trim + uppercase).

У ребёнка также виден полный список составляющих. Родители других поставщиков
не становятся дополнительными корнями, не получают самостоятельный прогноз и
не попадают в заказ. CSV/XLSX допускает только исходные закупаемые SKU выбранного
поставщика. Дети с BALL4 3/9/11/12 и любые товары с рецептом не закупаются.

## Рецепты и формула

- `ALL_RAZBORKA`: `ART` — родитель, `ART_R` — ребёнок, `KOL_R` — выход детей;
  расход родителя на ребёнка равен `1 / KOL_R`.
- `ALL_RAZBORKA_SLOJ`: `ARTIC_ROD` — родитель, `ARTIC_REB` — ребёнок,
  `KOL_R` — расход родителя на ребёнка, включая дробные количества.
- Наличие ребёнка в сложной таблице заменяет **весь** его простой рецепт,
  даже если сложный рецепт ошибочен. Автоматического возврата к простой таблице нет.
- `SCL_ARTC.BALL4` читается по участвующим складам. Отсутствующий, неизвестный или
  неодинаковый признак требует проверки. Несколько простых родителей, повтор одной
  составляющей, неположительный коэффициент, пустой артикул и самоссылка блокируют
  соответствующую ветвь. Источники ошибок сохраняют таблицу и Key в расшифровке.

Граф рассчитывается от листьев к корням без рекурсии. Для каждой группы склада:

```text
общая цель = собственный прогноз с MIN + сумма потребностей на изготовление детей
изготовить ребёнка = max(0, общая цель − запас для планирования − подтверждённые
                         поступления − поступления перемещением + выбытия перемещением)
расход составляющей = изготовить ребёнка × коэффициент составляющей
```

Запасы и поступления вычитаются один раз на каждом SKU. Общий ребёнок рассчитывается
один раз, но расходуется каждая фактическая составляющая. Промежуточные потребности
не округляются до упаковок/целых штук. У корня сохранены правила округления заказа.
Закупочный запрет у изготовляемого ребёнка не запрещает прогноз его изготовления;
MIN и все исходные метрики должны быть известны. Для детей сохраняются проверки
истории, прибыли, внутренних резервов, подтверждения и распределения транзита.
Ручная закупочная величина для ребёнка не применяется; редактируются поступления.

Детская потребность добавляется после ограничения собственного прогноза MAX;
превышение допустимого поступления корня требует проверки, а не скрытого урезания
потребности детей. Неизвестная потребность отображается `null`, блокирует предков
и никогда не считается нулём. Цикл блокирует свои вершины и предков; остальные
ветви сохраняют расчёт. Изменение поступлений ребёнка пересчитывает весь граф.

Пример бумаги: CL-96371CR3 потребляет 0,25 CL-96371CR, CL-96371CR4 — 0,2.
Это альтернативные раскрои (4 или 5 детей), не совместный выход 4 + 5 из листа.
Планирование не оптимизирует раскрой/остатки и не планирует мощности сборки.
Явное включение `МУЛЬТИСБОРКА` в продажи не допускается, чтобы не продублировать
расход, который уже рассчитан через детей. Накладная сборки со всеми родителями —
отдельная будущая функция; данный расчёт документов не создаёт.

## API и сессия

`POST /admin/folio/product-analytics/assembly-graph`:

```json
{"sourceDatabase":"Paint_Ua","warehouseIds":[1,7],"rootSkus":["CL-96371CR"]}
```

Заголовок `X-Auth-Token` должен совпадать с Java `lavka.token` (WordPress
`api_token`); отсутствующая настройка — 503, неверный токен — 401. Секрет не
передаётся браузеру. Разрешены Paint_Ua/Paint_Rus, проверяется фактический DB_NAME.
Доступ read-only через `folioJdbcTemplate`, SQL Server 2000, связанные параметры,
таймаут запроса 30 с, транзакция 60 с. Лимиты: 100 складов, 10 000 вершин,
200 000 строк в каждой таблице рецептов; превышение — ошибка, не усечение.

Ответ: `version:1`, SHA-256 `revision`, `nodes:[{sku,manufactured,issues}]`,
`edges:[{parent,child,factor,source,rowId}]`. Factor — расход родителя на единицу
ребёнка. Рёбра включают внешние составляющие для пояснения; в `nodes` только
исходные товары и их потребляющие потомки.

WordPress previewVersion=7: сначала страницы корней, затем запрос графа и страницы
недостающих детей пакетами по 100. До завершения экспорт недоступен. Финальный ответ
заменяет предварительные строки (`replaceItems`); корректировка возвращает весь
обновлённый набор `items`. Сессия фиксирует граф на два часа. Перед экспортом Java
читает граф снова: несовпадение revision требует нового preview. Цены/учётные
движения/документы в ФОЛИО не меняются. Новых миграций снимков не требуется;
используются существующие schema 7 и transit v3.
