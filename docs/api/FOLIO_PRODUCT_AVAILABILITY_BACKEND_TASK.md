# Задание Java: доступность товара за период и группы складов

Обновлено: 2026-09-03.

## Назначение

Добавить в product analytics отдельную метрику фактической доступности товара за
выбранный период. Она нужна для оценки упущенного спроса и качества пополнения
полок и не заменяет существующее покрытие запасом.

Текущий `metrics.coverageDays` сохраняет прежний смысл:

```text
max(availableQuantity, 0) * periodDays / regularSoldUnits
```

Это прогноз, на сколько дней хватит текущего запаса при прошлом регулярном
спросе. Переименовывать его в процент доступности или использовать как число
дней отсутствия нельзя.

## Бизнес-сценарии

1. Физический склад должен показывать собственную доступность. Если товар долго
   отсутствовал на складе 1, это видно даже тогда, когда он был на складе 7.
2. Логически объединённая группа показывает клиентскую доступность: товар
   считается доступным в день, когда он был хотя бы на одном применимом складе
   группы.
3. Пример группы Киева: склады 1 и 7. Это настройка, а не hardcode.
4. Пример группы Одессы: склады 5, 15 и 20. Это настройка, а не hardcode.
5. Если для SKU на физическом складе `MIN_TVRZAP=0`, склад не входит в
   ассортиментную матрицу этого SKU. Его отсутствие не считается stockout и не
   уменьшает процент доступности.
6. Если `MIN_TVRZAP` отсутствует или некорректен, backend возвращает
   `POLICY_NOT_CONFIRMED`; frontend не подменяет это нулём.
7. Если все склады группы неприменимы к SKU, результат группы —
   `NOT_APPLICABLE`, а не `0%`.

## Подтверждённые ограничения schema v4

- `dailyStockout` сейчас возвращается как `supported=false` с причиной
  `SOURCE_NOT_CONFIRMED`.
- В MariaDB нет подтверждённого подневного слоя доступности.
- История резервов по дням не подтверждена. Поэтому первая версия должна явно
  называться `PHYSICAL_END_OF_DAY`, а не обещать исторический свободный остаток.
- `MIN_TVRZAP` в текущем snapshot является состоянием на дату снимка. Пока нет
  истории ассортиментной политики, применять его ко всему выбранному периоду
  можно только с warning `CURRENT_POLICY_APPLIED_TO_PERIOD`.
- Нельзя получать число отсутствовавших дней из текущего остатка, месячного
  конечного остатка либо количества дней текущего покрытия.

## Источник и построение

Java должна восстановить физический остаток на конец каждого дня из:

- текущего `physicalQuantity` на дату активного snapshot;
- полного набора движений `affectsStock=true` и `signedQuantity` внутри
  горизонта;
- восстановленного входящего остатка на начало горизонта.

Для basis `PHYSICAL_END_OF_DAY` состояние дня определяется так:

- `AVAILABLE`, если физический остаток на конец дня строго больше нуля;
- `STOCKOUT`, если физический остаток равен нулю или отрицателен;
- `NOT_APPLICABLE`, если склад исключён для SKU правилом ассортиментной
  матрицы.

Отрицательный остаток дополнительно возвращается как предупреждение качества
данных, но не превращается в доступный день.

Если движение за период неполно или начальный остаток не сходится, доступность
для SKU получает `DATA_INCOMPLETE`, а не приблизительное число.

Для компактного хранения рекомендуется не создавать сотни миллионов обычных
daily rows. Канонический слой должен хранить доступность только для физического
склада (`SKU × warehouseId × day`). Допустимые варианты:

- интервалы непрерывного состояния `AVAILABLE/STOCKOUT`; либо
- месячная 31-битная маска доступных дней на `SKU × склад × месяц`.

Месячная битовая маска удобна для групп: группа использует логическое `OR` масок
только применимых складов, после чего считает дни в выбранной части месяца.

Состав объединённых складов нельзя записывать как неизменяемую часть товарного
snapshot. Это глобальная настройка WordPress и она может измениться без нового
движения товара. Java должна:

1. атомарно публиковать канонические маски/интервалы физических складов;
2. получать от WordPress актуальные группы и `warehouseGroupsRevision`;
3. рассчитывать группу из физических масок во время запроса; либо кэшировать
   вычисление с обязательным ключом `generationId + warehouseGroupsRevision`;
4. никогда не возвращать кэш другой ревизии;
5. при отсутствии нужного физического склада в generation возвращать явный
   статус, а не считать его нулевым остатком.

Так повторное переименование группы или изменение `1 + 7` не требует полного
перестроения истории. Перестроение требуется только при изменении алгоритма или
физических подневных данных.

Конкретное физическое хранение остаётся решением Java, HTTP-контракт от него не
зависит.

## Источник глобальной конфигурации групп

Источник истины находится в WordPress:

- taxonomy `location`;
- стабильный `term_id` и `slug` группы;
- term meta `lavka_folio_warehouses` с Folio ID и приоритетом;
- редактируемый `term.name` для интерфейса;
- SHA-256 ревизия нормализованного списка групп.

Сценарий аналитики хранит только выбранные склады или коды групп. Он не должен
копировать состав группы. WordPress разрешает выбранные коды через текущую
глобальную конфигурацию перед каждым запросом.

## Расширение запроса

`POST /admin/folio/product-analytics/query` должен принимать необязательный
блок:

```json
{
  "calculation": {
    "abcBasis": "GROSS_PROFIT",
    "includeReturns": true,
    "availability": {
      "enabled": true,
      "basis": "PHYSICAL_END_OF_DAY",
      "minimumStockEligibility": "CURRENT_POLICY_GT_ZERO",
      "presentation": "WAREHOUSES_AND_GROUPS",
      "warehouseGroupsRevision": "64-hex-sha256",
      "warehouseGroups": [
        {
          "code": "KYIV_SHARED",
          "name": "Київ, спільна доступність",
          "warehouseIds": [1, 7],
          "availabilityMode": "ANY_ELIGIBLE_MEMBER"
        },
        {
          "code": "ODESA_SHARED",
          "name": "Одеса, спільна доступність",
          "warehouseIds": [5, 15, 20],
          "availabilityMode": "ANY_ELIGIBLE_MEMBER"
        }
      ]
    }
  }
}
```

Правила валидации:

- группа содержит минимум один склад;
- каждый склад группы входит в `warehouseIds` запроса;
- `code` уникален внутри запроса;
- неизвестный режим возвращает HTTP 400;
- backend возвращает нормализованный блок в `appliedFilters`;
- определения групп не сохраняются в версии сценария: они всегда передаются из
  актуальной глобальной настройки WordPress;
- `warehouseGroupsRevision` обязателен, если передана хотя бы одна группа;
- нормализованные группы и их ревизия возвращаются в `appliedFilters` и в
  метаданных результата/экспорта;
- группы могут пересекаться только при явном разрешении контракта. В первой
  версии безопаснее запретить пересечение.

## Расширение ответа

Для общей строки SKU:

```json
{
  "availability": {
    "status": "MEASURED",
    "basis": "PHYSICAL_END_OF_DAY",
    "periodDays": 123,
    "eligibleDays": 123,
    "availableDays": 104,
    "stockoutDays": 19,
    "availabilityPercent": 84.55,
    "stockoutPercent": 15.45,
    "warnings": ["CURRENT_POLICY_APPLIED_TO_PERIOD"]
  }
}
```

В каждый `warehouseBreakdown[]` добавить:

```json
{
  "availability": {
    "status": "MEASURED",
    "eligible": true,
    "minimumStock": 3,
    "periodDays": 123,
    "eligibleDays": 123,
    "availableDays": 88,
    "stockoutDays": 35,
    "availabilityPercent": 71.54,
    "stockoutPercent": 28.46
  }
}
```

Отдельно вернуть `warehouseGroupBreakdown[]`:

```json
{
  "code": "KYIV_SHARED",
  "name": "Київ, спільна доступність",
  "warehouseIds": [1, 7],
  "availabilityMode": "ANY_ELIGIBLE_MEMBER",
  "availability": {
    "status": "MEASURED",
    "periodDays": 123,
    "eligibleDays": 123,
    "availableDays": 121,
    "stockoutDays": 2,
    "availabilityPercent": 98.37,
    "stockoutPercent": 1.63
  }
}
```

`rows[].availability` для нескольких складов не должно быть средним процентом.
Backend либо рассчитывает объединение выбранного контекста по дням, либо
возвращает `null` с явным статусом. Интерфейс в первую очередь показывает
физические склады и настроенные группы; неявное объединение всех выбранных
складов запрещено.

Минимальные статусы:

```text
MEASURED
NOT_APPLICABLE
POLICY_NOT_CONFIRMED
DATA_INCOMPLETE
PERIOD_OUTSIDE_HORIZON
SNAPSHOT_NOT_READY
```

## Capabilities и сценарии

`POST /admin/folio/product-analytics/capabilities` после реализации возвращает:

```json
{
  "filters": {
    "dailyStockout": {"supported": true}
  },
  "features": {
    "availability": {
      "supported": true,
      "basis": ["PHYSICAL_END_OF_DAY"],
      "groupModes": ["ANY_ELIGIBLE_MEMBER"],
      "minimumStockEligibility": ["CURRENT_POLICY_GT_ZERO"]
    }
  }
}
```

До этого ответа WordPress не показывает процент как рабочую метрику и не
вычисляет его самостоятельно. После поддержки WordPress добавляет блок
`calculation.availability` во время выполнения. Глобальный состав групп не
сохраняется в сценарии и не участвует в определении, был ли сценарий временно
изменён. Старые сценарии продолжают работать без миграции.

## Экспорт

WordPress экспортирует весь отфильтрованный результат в CSV и настоящий XLSX.
Поэтому cursor-пагинация `/query` должна быть стабильной для всех строк одного
активного generation. В каждой строке экспорта должны быть доступны:

- `coverageDays` без изменения формулы;
- общий подтверждённый `availability` либо явный статус;
- физический `warehouseBreakdown[].availability`;
- `warehouseGroupBreakdown[].availability`;
- применённая `warehouseGroupsRevision`.

Добавить server-side фильтры и сортировку:

- `availabilityPercent` от/до;
- `stockoutPercent` от/до;
- `availabilityStatus`;
- физический склад либо код настроенной группы.

## Проверочные примеры

1. Период 30 дней. Склад 1 доступен первые 20 дней, склад 7 — последние 10.
   Физические результаты: `66,67%` и `33,33%`; группа Киева — `100%`.
2. Склад 7 отсутствует все 30 дней, но `MIN_TVRZAP=0`. Он получает
   `NOT_APPLICABLE` и не уменьшает результат группы.
3. У всех членов группы `MIN_TVRZAP=0`. Группа получает `NOT_APPLICABLE`, не
   `0%` и не `100%`.
4. На складе 1 доступность `60%`, на складе 7 — `100%`. Группа может показать
   `100%`, но детализация склада 1 обязана сохранить `60%`, чтобы было видно
   проблему выкладки товара.
5. При отсутствии подневного источника backend возвращает `DATA_INCOMPLETE` и
   `null` вместо вычисления из текущего остатка.
6. Итоги по группам пересчитываются из дневных масок/интервалов и не являются
   средним процентов участников.

## Definition of Done

- построение snapshot остаётся read-only для ФОЛІО;
- новая проекция публикуется атомарно вместе с generation;
- физические дневные данные являются каноническими, а групповые значения не
  переживают смену `warehouseGroupsRevision` в старом кэше;
- schema version повышена, старые поколения дают понятную ошибку;
- проверены границы периода и неполные месяцы;
- минимум 10 SKU сверены вручную по движениям двух физических складов;
- отдельно проверены `MIN_TVRZAP=0`, неизвестная политика и объединённая группа;
- текущий `coverageDays` не изменил формулу и не исчез из ответа;
- документация API и frontend handoff обновлена в Java-репозитории.
