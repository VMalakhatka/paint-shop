# Нова пошта: перевірка контракту створення, друку та трекінгу

## Доповнення: реєстр і перевірка охоплення — 25.10.2026

Після ручного проходження Cloudflare користувачем повторно прочитано у Chrome
[getDocumentList](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/a9d22b34-8512-11ec-8ced-005056b2dbe1).
Портал підтверджує `InternetDocument` у тексті, `InternetDocumentGeneral` у прикладі,
`GetFullList=0` + Page до 100 записів. Фільтр дат — дата відправлення,
за відсутності — створення ІД; без дати/номера — поточний день.
Реєстр 0.10.0 використовує текстовий контракт `InternetDocument`, явний період
та сторінки. Живе читання 25.10.2026 підтвердило відмову за період
01.06–25.10.2026: різниця DateTimeFrom/DateTimeTo не може перевищувати три місяці.
Окремі читання першої сторінки за червень та 1–25 жовтня повернули success=true
і відповідно 1 та 8 рядків. Це перевірка читання, не збереження в реєстрі й не
доказ повноти історії. 0.10.1 ділить вибраний період на календарні місяці з
посторінковим читанням кожного; до його публікації місяці вибирають вручну.

Документація описує список ЕН, доступних особистому кабінету, але не обіцяє
повне охоплення вхідних чи всі історичні події з 01.06.2026. Параметр
`RedeliveryMoney=1` стосується зворотної грошової доставки; це не прапорець
«усі вхідні посилки». Поки не використовується як спосіб виявлення вхідних.

Також прочитано [generateReport](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/aa1b448f-8512-11ec-8ced-005056b2dbe1):
метод вимагає вже відомі `DocumentRefs`, `Type=csv/xls`, `DateTime`.
Він не підтверджує пошук невідомих вхідних; опис відповіді містить розбіжності,
тому універсальний імпортер його експорту не заявляється й метод не викликається.
API-консоль, реальні ТТН, повідомлення та production-імпорт не запускались.

Окремий реєстр підтримує відомі вхідні ТТН через перевірений tracking-контракт,
явний CSV-шаблон і ручне внесення з доказом. Межі джерел, NULL-суми, знімки
та прив’язки ФОЛІО описані в [README 0.10.0](../../wp-content/plugins/paint-nova-poshta-multishipping/README.md#shipment-registry-0100--2026-10-25).

Перевірено: 2026-10-18, офіційний developer portal у відкритій вкладці Chrome.
Власник реалізації: `paint-nova-poshta-multishipping`; адаптер менеджера — PCOE.
Це результат читання документації, **не результат створення реальної ТТН**.
API-консоль не запускалася; ключі, клієнтські дані та production options не змінювалися.
Попередній HTTP 403 не є поточним блокером доступу: у браузері сторінки доступні.

Реліз 0.9.0 реалізував обмежений цикл create/PDF/email з локальними fixtures.
У 0.9.1 окремо погоджено один живий запис одержувача без по батькові, без ТТН.
Статус реалізації, тести та
write-gates: [README плагіна](../../wp-content/plugins/paint-nova-poshta-multishipping/README.md).
Дії менеджера: [підготовка НП](../MANAGER_CUSTOMER_GUIDE_UK.md#np-preparation).

## Створення: підтверджено документацією

[Базовий save](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/a965630e-8512-11ec-8ced-005056b2dbe1)
описує `InternetDocument.save`; JSON-приклад використовує
`modelName=InternetDocumentGeneral`. Не змінювати модель вже працюючих read-методів
лише на підставі назви прикладу. Для нового create-клієнта зафіксувати обраний
контракт у fixtures та перевірити його в окремо дозволеному пілоті.

JSON endpoint: `https://api.novaposhta.ua/v2.0/json/`. Тіло: `apiKey`, `modelName`,
`calledMethod`, `methodProperties`. HTTP 200 може містити бізнес-помилку;
перевіряти `success`, `errors`, структуру `data`, `Ref` і `IntDocNumber`.
Успішна відповідь також містить `CostOnSite`, `EstimatedDeliveryDate`, `TypeDocument`.
`warnings` не прирівнювати до невдалої операції чи підстави повторити `save`.

Основні поля `methodProperties`:

- `PayerType`: Sender / Recipient / ThirdPerson; `PaymentMethod`: Cash / NonCash.
  Підтримка API не означає автоматичного дозволу всіх варіантів нашою політикою.
- `ServiceType`: WarehouseWarehouse / WarehouseDoors / DoorsWarehouse / DoorsDoors.
- `DateTime`: `dd.mm.yyyy`; максимальна майбутня дата — створення + 3 місяці.
  При перевищенні API коригує дату й повертає warning разом з успіхом.
- `CargoType`, `SeatsAmount`, `Description`, `Cost` (оголошена вартість).
- `Weight`: фактична вага у кг, мінімум 0.1. `VolumeGeneral`: м³, мінімум
  0.0004; потрібний, якщо немає `OptionsSeat`.
- Відправник: `CitySender`, `Sender`, `SenderAddress`, `ContactSender`, `SendersPhone`.
- Одержувач у Ref-варіанті: `CityRecipient`, `Recipient`, `RecipientAddress`,
  `ContactRecipient`, `RecipientsPhone`.
- `SenderWarehouseIndex` / `RecipientWarehouseIndex` — цифрові адреси точок,
  не UUID Ref. Не підміняти ними зареєстровану адресу чи Ref без перевірки контракту.

[Створення до відділення рядком](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/a19ced79-8f32-11ec-8ced-005056b2dbe1)
використовує `NewAddress=1`, `RecipientCityName`, `RecipientArea`,
`RecipientAreaRegions`, `RecipientAddressName` (номер відділення),
`RecipientName`, `RecipientType`, `SettlementType`, `RecipientsPhone`.
Для відділення `RecipientHouse` і `RecipientFlat` не заповнюють.
`SettlementType` береться з адресного довідника, не вгадується з назви міста.
Не переносити до цього варіанта Ref-поля з іншого прикладу без підтвердження.

## Поштомат і коробки

[Окремий контракт поштомата](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/0227072e-8f38-11ec-8ced-005056b2dbe1)
у текстових правилах дозволяє Parcel / Documents, лише одне місце, до 20 кг,
ширину 40 см, довжину 60 см, висоту 30 см та оголошену вартість до 29 000 грн.
Це загальні обмеження документації на дату перевірки, а не заміна актуальної
картки конкретної точки. Майбутній preflight має перевіряти обидва джерела;
розбіжність не означає дозвіл застосувати м'якшу межу.

`OptionsSeat` — масив місць: `weight` у кг; `volumetricWidth`,
`volumetricLength`, `volumetricHeight` у см; `volumetricVolume` у м³.
Розрахунок об'єму з наших сантиметрів: `length * width * height / 1000000`.
Це об'єм, не об'ємна вага. Не передавати см³ як м³.

**Розбіжність джерела:** JSON-приклад цієї ж сторінки містить Cargo та два місця,
хоча текст прямо забороняє їх для поштомата. Приклад не є валідною тестовою
відправкою. Не копіювати його дослівно; застосовувати суворі текстові правила та
перевіряти прийнятність payload перед дозволеним пілотом.

## Друк: підтверджено документацією

[Маркування](https://developers.novaposhta.ua/view/model/a3fe2fdd-8512-11ec-8ced-005056b2dbe1/method/a40fb782-8512-11ec-8ced-005056b2dbe1)
повертає форму за Ref або номером ТТН. Шаблони серверних URL, лише placeholders:

```text
https://my.novaposhta.ua/orders/printMarking85x85/orders[]/{REF}/type/pdf8/apiKey/{KEY}
https://my.novaposhta.ua/orders/printMarking100x100/orders[]/{REF}/type/pdf/apiKey/{KEY}/zebra
```

Перший — A4 (6 наклейок), другий — Zebra. Для пакетної печаті документація
вказує типову межу 100 маркувань і параметри `limit` / `page`.

**Реалізовано у 0.9.0:** URL з ключем формує тільки сервер.
Не показувати його в HTML, редиректі, листі, браузері або логах. Потрібний власний
авторизований endpoint: capability + nonce + належність shipment замовленню,
allowlist хоста/формату, таймаут/межа розміру, перевірка MIME та PDF-сигнатури,
заборона довільних редиректів і приватна видача без кешування.
Зовнішні ТТН клієнта не отримують права на друк через ключ магазину.

[PDF експрес-накладної](https://developers.novaposhta.ua/view/model/a3fe2fdd-8512-11ec-8ced-005056b2dbe1/method/a4583ee4-8512-11ec-8ced-005056b2dbe1),
прочитано 18.10.2026: `/orders/printDocument/orders[]/{REF}/type/pdf/apiKey/{KEY}`.
Використовується той самий приватний transport; жодних HTML-редиректів.

## Одержувач за Ref і розрахунок, додатково прочитано 18.10.2026

[CounterpartyGeneral.save](https://developers.novaposhta.ua/view/model/a28f4b04-8512-11ec-8ced-005056b2dbe1/method/0ae5dd75-8a5f-11ec-8ced-005056b2dbe1)
створює PrivatePerson/Recipient: FirstName, LastName, MiddleName, Phone;
імена українською, кожне до 36 символів. Таблиця позначає MiddleName обов'язковим,
але погоджена жива перевірка 18.10.2026 підтвердила `MiddleName: ""`:
HTTP 200, `success=true`, один Ref одержувача, ContactPerson.success=true,
Ref контакту та порожній ContactPerson.data[0].MiddleName. Один запит save,
без ТТН, друку, повідомлень або зміни Woo. Персональні дані/Ref у документації
не зберігаються. У 0.9.1 відсутнє по батькові серіалізується порожнім рядком.
Email необов'язковий і в нашому payload не передається.
Відповідь: data[0].Ref контрагента та вкладений ContactPerson із success/data/Ref.
Офіційний JSON приклад синтаксично пошкоджений; XML підтверджує вкладену структуру.
Парсер приймає один object або singleton list ContactPerson, лише з явним
success=true та одним валідним Ref. Невідомі/неоднозначні форми блокують наступний
save, не повторюють створення. Це додає одержувача в довідник НП, не в Woo-профіль.

0.9.1/0.9.2 помилково вимагали Phones безпосередньо у відповіді save, хоча
офіційні приклади його не містять. Моки були надто повними; не вважати їх
доказом фактичної форми відповіді перевізника.

У 0.9.3 Ref одержувача/контакту зберігаються до додаткового читання.
[getCounterpartyContactPersons](https://developers.novaposhta.ua/view/model/a28f4b04-8512-11ec-8ced-005056b2dbe1/method/a3575a67-8512-11ec-8ced-005056b2dbe1),
прочитано у Chrome 18.10.2026: модель у тексті Counterparty, JSON-приклад
CounterpartyGeneral; Ref контрагента та Page, до 100 контактів на сторінку.
Відповідь містить Ref, FirstName, LastName, MiddleName і Phones (string).
Живе читання через Counterparty підтвердило ці поля й один точний збіг
погодженого контакту. Пошук контрагента за прізвищем дав порожній список;
контакт знаходиться всередині контрагента PrivatePerson, тому такий пошук
не доводить відсутності одержувача. Сторонні контакти не зберігаються.

0.9.3 вимагає збіг полів окремо прочитаного точного контакту із
підтвердженим запитом (MiddleName порівнюється, якщо його введено).
Нормалізуються регістр, пробіли, апострофи й формат українського телефону, без
нечіткого зіставлення. Неповні/інші дані дають `np_recipient_mismatch` до
InternetDocumentGeneral.save; автоматичних повторів немає. Поведінку цієї
захисної гілки перевірено mock-тестами, не реальною ТТН.
Не називати її перевіркою власника телефону: глобального phone-to-person API
не підтверджено. Точкове getCounterparties з FindByString за прізвищем повернуло
порожній список; це не доказ відсутності людини в НП. Перелік чужих контактів
не вивантажувався. Подальше дослідження пошуку потребує перевіреного контракту.

Для поштомата обрано саме документований Ref-варіант; рядковий RecipientName
не змішується з ним. До InternetDocumentGeneral.save підставляються Recipient та
ContactRecipient з перевіреної відповіді попереднього save. Початковий durable
claim передує обом записам; між ними зберігається точний payload документа.

[getDocumentPrice](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/a91f115b-8512-11ec-8ced-005056b2dbe1)
підтверджує OptionsSeat з weight і габаритами у см. Preview передає міста,
ServiceType, CargoType, Cost, Weight, SeatsAmount і OptionsSeat, читає data[0].Cost.
Таблиця CargoType цієї сторінки не перелічує Parcel, хоча контракт поштомата
вимагає Parcel. Передається тип майбутньої накладної без непомітної підміни;
якщо API відмовить у розрахунку, створення не дозволяється. Це потребує
окремо дозволеного live-пілота; fixtures не доводять прийняття реальним НП.

## Трекінг: підтверджено документацією

[getStatusDocuments](https://developers.novaposhta.ua/view/model/a99d2f28-8512-11ec-8ced-005056b2dbe1/method/a9ae7bc9-8512-11ec-8ced-005056b2dbe1)
описаний для `TrackingDocument`, JSON-приклад — `TrackingDocumentGeneral`.
`Documents` містить `DocumentNumber` і, за потреби розширених даних, `Phone`;
до 100 документів у запиті. API-ключ і успішна валідація потрібні для повних
даних. Неавторизований результат не є доказом особи відправника/одержувача.

Значення кодів, потрібні для наступної реалізації:

| Коди | Значення за документацією | Проєктне трактування повідомлення |
|---|---|---|
| 1 | Накладна створена, вантаж ще не переданий | Лише «підготовлено», не «відправлено» |
| 2 / 3 | Видалена / номер не знайдено | Не надсилати повідомлення про відправку |
| 4 / 41 / 5 / 6 | Вантаж у логістичній мережі / прямує між містами | Свідчення фізичного руху, а не самого створення |
| 7 / 8 | Прибуття до відділення / поштомата | Вантаж уже переданий перевізнику |
| 9 / 10 / 11 | Отримано; варіанти стану грошового переказу | Доставлено; не підтвердження нашого банківського платежу |
| 101 | Доставка до одержувача | Фізичний рух |
| 102 / 103 / 104 / 105 / 106 / 107 / 111 / 112 / 124 | Відмова, зміни, повернення або інші спеціальні стани | Окрема обробка, не універсальне «відправлено» |

Повідомлення — наш висновок із офіційних значень, не готовий алгоритм у релізі.
Невідомий код зберігати як невідомий; не вважати будь-який код > 1 успішною
відправкою. Зберігати час перевірки; помилка нового опитування не доводить
скасування чи доставки. Дедуплікація сповіщень потрібна окремо від polling.

## Невідомий результат створення

### Обмеження частоти: перевірено живим читанням 18.10.2026

`Address.getWarehouses` під час послідовної перевірки відділення та поштомата
повертав HTTP 200, `success=false`, `errorCodes=["20000401501"]`,
`errors=["To many requests"]`. Це підтверджений код конкретної відмови, не
підтвердження універсального числового ліміту НП. 0.9.2 розпізнає також HTTP 429
і написання `Too many requests`. Явний allowlist read-методів дозволяє лише один
повтор після cooldown; інші бізнес-помилки й транспортні timeout не повторюються.
`save` ніколи не повторюється, навіть за 429. Технічні інтервали, lock і тести:
[README плагіна](../../wp-content/plugins/paint-nova-poshta-multishipping/README.md#request-pacing-092--2026-10-18).

### Ручна звірка створення

[getDocumentList](https://developers.novaposhta.ua/view/model/a90d323c-8512-11ec-8ced-005056b2dbe1/method/a9d22b34-8512-11ec-8ced-005056b2dbe1)
дозволяє пошук за `DateTime` / `DateTimeFrom` + `DateTimeTo` або `IntDocNumber`.
Без дати й номера повертає поточний день. `GetFullList=1` обмежений 100 записами;
для повної вибірки потрібні `GetFullList=0` і `Page` (до 100 на сторінку).
Відповідь містить Ref/номер, дати, міста/адреси, вагу, кількість місць, вартість,
платника та `StateId` / `StateName`.

У перевірених сторінках не підтверджено carrier-side idempotency key чи пошук за
нашим UUID. Локальний ключ не гарантує дедуплікацію на боці НП. Після timeout:
залишити `unknown`, не повторювати `save`; список може бути джерелом для ручної
звірки, але не доказом відсутності ТТН. Збіг дати/міста/суми сам по собі не дає
права автоматично прив'язати чужу накладну.

## Залишається реалізувати / уточнити

- Реальний дозволений пілот уже реалізованого обмеженого payload, остаточна
  звірка формату ContactPerson, Parcel quote, адреси передачі та угоди платника.
- Узгодити розбіжності прикладів: назви моделей з `General`, оголошена вартість
  за замовчуванням 300.00 / 300.01, обов'язковість організаційних полів у
  PrivatePerson-прикладі. Не використовувати defaults замість явної вартості.
- Окремо перевірити адресний варіант і COD-контракт; кілька складів з COD
  залишаються забороненими до погодженого правила. Не припускати, що наявність
