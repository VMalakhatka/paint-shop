# WayForPay → банковский приход ФОЛИО

Проверено: 2026-10-16. Задание реализовано в `pc-wayforpay-checkbox` 0.2.0
и Java `folio.payment`, по умолчанию выключено. Production-запуск ещё не выполнен.

Основной операторский документ: [FOLIO_WFP_PAYMENTS.md](../FOLIO_WFP_PAYMENTS.md).
Точный контракт: Java-репозиторий, `docs/api/FOLIO_WFP_PAYMENTS_API.md`.

## Уточнённое решение владельца

Первоначальное требование обязательного распределения на счёт **заменено**:
подтверждённая оплата сама является основанием для банковского прихода.
Счёт отсутствует, частично покрыт, разделён, изменён или архивирован — приход
всё равно создаётся на полную сумму поступления. Распределение по счетам отдельно.

Все поступления ФОП Малахатка: склад5, вид операции МАЛАФОП, тип РЕАЛИЗАЦИЯ.
Плательщик фиксируется по привязке покупателя при первом проверенном Approved,
включая штатного Интернет клиента. Изменение профиля не переносит старый приход.

## Владелец реализации

- WordPress Bridge проверяет подпись/merchant/reference/сумму/UAH/Approved1100,
  сохраняет снимок плательщика и время подтверждения до Woo payment_complete.
- Отдельная очередь `pc_wfp_folio_payments` не ждёт Checkbox или счёта.
- Java предоставляет preview/apply/status, проверяет dedicated token,
  конфигурацию, плательщика и банковский шаблон. Native INSERT_PLAT и запись
  `LAVKA_WFP_PAYMENTS` фиксируются одной serializable MSSQL-транзакцией.
- Исходный приход не распределён: `NACLAD_POR=0`, `NOTOVAROST=SUM_POR`,
  строк SCL_PMOV нет. Наличие счёта не проверяется.
- Дубли возвращают прежний результат. После неопределённого apply только GET;
  404 не разрешает повторную отправку. Секретов и сырых callback в журнале нет.
- Возврат WFP не удаляет факт поступления: требуется отдельная расходная
  операция. Автоматические расходы и распределение ещё не реализованы.

## Проверки и история

Ранее один отдельно разрешённый production-приход был проведён с распределением
на восстановленный счёт. Владелец подтвердил его видимость в ФОЛИО. Это ручная
recovery, а не автоматический журнал. Для неё сохраняется приватная метка
`_folio_manual_payment_recovery`; новый consumer не создаёт её повторно.

После нового решения выполнена отдельная синтетическая проба Paint_Rus:
банковский приход без счёта, сумма4, нераспределено4, склад5, аллокаций0.
Native return0, внешняя транзакция сохранена, rollback подтверждён; независимый
postcheck подтвердил отсутствие тестовых партнёра/прихода/аллокаций/TMP.
NULL в NACLAD_POR оказался недопустим; схема/default и существующие документы
подтвердили штатное значение0. Не подменять отсутствие счёта фиктивным ID.

Обезличенные доказательства, воспроизводимый rollback SQL и ограничения:
Java `docs/api/FOLIO_WFP_PAYMENTS_API.md` и
`docs/folio-experiments/2026-10-16-unallocated-payment-*.sql`.
Предыдущее исследование связанного прихода:
`docs/folio-experiments/2026-10-16-payment-procedure-fingerprints.md`.

## Оставшийся production-этап

Отдельно согласовать и выполнить DDL журнала/права, deployment обоих компонентов,
конфигурацию и новый cutoff, preview, один новый live-платёж и сверку ФОЛИО UI/долга.
Старые оплаты автоматически не подхватывать. Точная последовательность,
пауза и безопасное восстановление — в основном документе выше.
