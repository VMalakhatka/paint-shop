# WayForPay → банковский приход ФОЛИО

Статус: **согласованное задание, не действующий API**. Проверено: 2026-10-16.
Источник бизнес-правил — решения владельца; текущего поведения — PHP/Java-код
и read-only production-аудит. Операторская точка входа:
[WayForPay](../WAYFORPAY_TEST_ACCESS.md#банковская-оплата-в-фолио--согласовано-ещё-не-реализовано).

## Согласованные правила

- Только проверенное сервером успешное `Approved` / `1100` уведомление WFP:
  подпись, merchant, reference, сумма, валюта. Browser return, Woo `processing`
  и одна лишь отметка `WFP` не являются основанием для создания прихода.
- Все оплаты ФОП Малахатка записываются в платёжный склад **5**, независимо от
  склада счёта и товара. Это бизнес-конфигурация получателя, не вычисление по
  доставке, адресу покупателя или названию склада. Не переносить товар/резервы.
- Документ «Приход по банку», вид операции `МАЛАФОП`, тип операции
  `РЕАЛИЗАЦИЯ`, учитываемый, с учётом суммы в расчёте долгов — по образцу владельца.
  Номер, дата, сумма и контрагент из скриншота не являются defaults.
- Оплату распределять на счёт, созданный из заказа. Идентичность плательщика
  брать из сохранённого счёта ФОЛИО, не из изменяемого user meta при повторе.
- Новые customer без отдельной связи используют штатного «Интернет клиента»;
  персональная связь менеджера сохраняется. Уже созданные финансовые документы
  не переносятся автоматически при переназначении пользователя.
- Чек Checkbox и приход ФОЛИО — независимые последствия одной подтверждённой
  оплаты. Повтор проверки чека не создаёт платёж; повтор прихода не создаёт чек.

## Владельцы и текущий пробел

`pc-wayforpay-checkbox/src/Bridge.php` проверяет callback и сохраняет уникальную
операцию в `pc_wfp_receipts` до `payment_complete`. `pc-folio-order-link.php`
создаёт счета и хранит `_folio_documents_result`. `WFP` в `additionalInfo`
сейчас не создаёт `SCL_PLAT` и не распределяет оплату.

Java владеет MSSQL-транзакцией и native semantics; WordPress не пишет в MSSQL.
Отдельного write API банковских приходов в исследованном Java-коде нет.
Customer-documents API читает `linkedPayments`, но не создаёт их.
Backend-контракт после реализации должен жить в Java `docs/api`; этот документ
остаётся заданием и должен ссылаться на принятый контракт, а не дублировать его.

## Обязательные свойства реализации

1. Сохранять отдельное намерение учётной оплаты при проверенном callback, до
   внешнего HTTP. Доставка через отдельную очередь; состояние не привязывать к
   успешности Checkbox. Сбой ФОЛИО не теряет подтверждённую оплату WFP.
2. До появления счёта ожидать его существующую операцию; worker оплаты не
   вызывает повторный create счёта. После появления зафиксировать технический
   ID, плательщика, сумму и revision/fingerprint источника. Видимый номер не ключ.
3. Один внешний платёж — одна идемпотентная команда: scope сайта/merchant +
   reference. Тот же ключ с другим каноническим payload — conflict. Повтор с тем
   же payload возвращает прежний результат. Не копировать секрет merchant.
4. Запись idempotency и полный банковский приход/распределение должны commit-иться
   в одной MSSQL-транзакции. WordPress marker не заменяет эту гарантию. Новая DDL
   выполняется отдельным согласованным deployment, не на HTTP-запросе.
5. HTTP auth fail closed, серверная проверка источника счёта и его плательщика;
   одного ID счёта от браузера недостаточно. Источник callback — только WFP adapter.
6. Сумма команды в копейках; Java использует `BigDecimal`. Сверять captured gross,
   суммы счёта/распределений и уже оплаченные количества. Комиссию эквайринга не
   вычитать молча из оплаты покупателя. Доставка/скидки/округление/нехватка товара
   не могут стать необъяснённой разницей: несовпадение блокирует apply.
7. При split не создавать по одному полному приходу на каждого Woo child.
   Нужны все исходные счета, единый плательщик и точное распределение одной суммы.
   До доказанного split mapping останавливать такой случай для review.
8. Проверять возврат WFP перед первой записью. Подтверждённый refund переводить
   в review; не создавать поздний приход и не удалять уже проведённый.
   Возврат банковской оплаты — отдельная будущая операция.
9. Сохранять время подтверждения UTC и отдельно дату учёта в согласованной
   business timezone. Не брать дату callback-повтора или текущее время worker.
10. Таймаут/потеря ответа после отправки — unknown outcome. Сначала status lookup
    по прежнему ключу, не новый номер/ключ/POST. Нужны защита от конкуренции и
    тест падения между MSSQL commit и сохранением результата WordPress.
11. В заказе показывать отдельный статус оплаты ФОЛИО, номер прихода, техническую
    связь и безопасную ошибку. Capability/nonce для recovery; английские msgid,
    UK/RU переводы. Не раскрывать токены, банковские реквизиты и сырые callbacks.
12. Default off, отдельные preview/apply, start boundary и kill switch. Выпуск
    кода не запускает старые оплаты. Backfill только по согласованному списку.

## Что уже установлено статическим разбором

Источник: snapshot SQL definitions Paint_Ua от 2026-08-11, просмотр выбранных
объектов 2026-10-16; это **не golden-master новой реализации и не живая проверка**.

- `INSERT_PLAT` делегирует `i_ins_plat`.
- `i_ins_plat` читает строки из persistent `TMP_MOVE`, создаёт `SCL_PLAT` и
  `SCL_PMOV`, меняет оплаченные количества/суммы `SCL_MOVE` и признаки оплаты
  `SCL_NAKL`. У неё собственные transaction statements и очистка `TMP_MOVE`.
- Процедура может добавлять справочные значения. Не запускать её с произвольными
  defaults или неизвестным TMP-ключом, даже как «проверку связи».
- `I_GET_LAST_PLAT_NUM` использует правила номера банковского платежа с настройкой
  scope через `NSF_ORG`. Нельзя копировать allocator счёта `NSF_ORG.N_3` или
  использовать незащищённый `MAX + 1`.
- Подтверждённое UI mapping: `SCL_PLAT.VID_DOC` — вид операции,
  `L_NAME_POR` — имя плательщика, `ORG_PREDM` — short name,
  `DOCUMN_POR` — примечание, `STND_UCHET` — учёт.
  Остальные значения, включая точный debt flag и дополнительные реквизиты,
  требуют свежей схемы и сравнения со штатным клиентом.

## Блокирующая проверка на копии

После подтверждения владельцем VPN и наличия восстановимой копии лаборатория
запущена. Preflight 2026-10-16 14:20:59 UTC: `Paint_Rus`, SQL Server `8.00.760`,
compatibility `80`, CP1251; изоляция подтверждена, `safeToRun = true`.
Дата последнего успешного восстановления не сообщена; test restore не выполнялся.

С отдельного разрешения добавлен фиксированный read-only endpoint лаборатории
`GET /api/v1/procedure-fingerprints/payments`. Он возвращает хеши только четырёх
платёжных процедур, не SQL-текст; общий запрет выгрузки исходников сохранён.
Все четыре нормализованных SHA-256 совпали с локальным снимком после восстановления
трёх CRLF, потерянных форматом RPT. Это сверка версий копии, не production audit.
Java evidence: `docs/folio-experiments/2026-10-16-payment-procedure-fingerprints.md`.
Платёжные процедуры не исполнялись, банковский приход не создавался;
production deploy не выполнялся. Эксперимент с оплатой/откатом остаётся впереди.

Этапы проверки (health и сверка версий выполнены; остальные не считать пройденными):

1. Health/preflight, изоляция login, точная БД/версия/collation, backup/restore gate.
2. Свежие columns/defaults/PK/FK/identity/triggers для `SCL_PLAT`, `SCL_ADDP`,
   `SCL_PMOV`, `TMP_MOVE`, затрагиваемых `SCL_MOVE`/`SCL_NAKL`; выбранные определения
   procedures. Ни metadata probe, ни preview не вызывают мутирующие procedures.
3. Synthetic клиент/счёт/товар, отдельный baseline; однозначно сопоставить поля
   штатного банковского прихода, учёт долга, дополнительные реквизиты и нумерацию.
4. Один разобранный сценарий оплаты с внешним rollback; проверить транзакционную
   границу, before/after, точный состав распределения и неизменность склада товара,
   физического остатка/резерва. Независимое чтение после rollback обязательно.
5. Сверить результат штатным отчётом/клиентом. Не обобщать одну полную оплату на
   частичную, split, возврат, архив и валютный сценарий.
6. Реализовать Java write contract и PHP consumer, unit/contract/concurrency tests;
   только затем согласовать deployment и один конкретный production apply.

При неизвестном результате либо нарушении boundary не повторять операцию и не
удалять документы «для очистки». Сначала независимая сверка. Наличие credentials,
скриншота, HTTP 200 или созданного чека не заменяет этот gate.
