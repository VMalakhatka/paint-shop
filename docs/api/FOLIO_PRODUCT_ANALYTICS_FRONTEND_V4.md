# Товарная аналитика ФОЛІО schema v4 в WordPress

Проверено: 2026-08-31 по Java-контракту schema v4 (`f417ecc`) и коду
`lavka-price-sync`.

Статус: реализовано в WordPress. Для фактической работы Java schema v4 должна
быть задеплоена, а выбранные склады должны иметь совместимые активные снимки
`ACTIVE / COMPLETED` версии 4.

## Поток данных

```text
браузер менеджера
  -> WordPress admin-ajax.php + nonce + LPS_CAP
  -> Java /admin/folio/product-analytics/*
  -> активные snapshot schema v4 в MariaDB
```

Браузер не обращается напрямую к Java, MariaDB или ФОЛІО. WordPress не
пересчитывает прибыль, маржу, GMROI, оборачиваемость, покрытие или общие итоги.

## WordPress proxy

Обе операции выполняются `POST` к `wp-admin/admin-ajax.php`.

### Возможности выбранных складов

```text
action=lps_product_analytics
operation=v4_capabilities
_ajax_nonce=<nonce>
payloadJson={"sourceDatabase":"Paint_Ua","warehouseIds":[1,5,7]}
```

WordPress проверяет право `LPS_CAP`, nonce, базу и номера складов, затем вызывает:

```http
POST /admin/folio/product-analytics/capabilities
```

Запрос повторяется после изменения набора складов. Рабочими показываются только
фильтры с `supported=true`. Коды значений берутся из `dictionaries`.

### Построение отчёта

```text
action=lps_product_analytics
operation=v4_query
_ajax_nonce=<nonce>
payloadJson={...schema v4 query...}
```

WordPress очищает и ограничивает входные данные, после чего вызывает:

```http
POST /admin/folio/product-analytics/query
```

Ответ Java передаётся интерфейсу без повторного вычисления. Ошибки 400, 409 и
503 сохраняют `code`, `message`, HTTP-статус и безопасное тело ответа.

## Экраны

### Товарная аналитика ФОЛІО

- выбор одного или нескольких складов;
- период и база ABC;
- точный SKU и основной GTIN;
- динамические `INCLUDE / EXCLUDE / ANY` для поддержанных условий товара и
  движений;
- вкладки «Товари» и «Рух товару» на одном серверном результате;
- общие итоги всей выборки, а не только страницы;
- cursor-пагинация;
- детализация складов, MIN/MAX и готовой политики заказа;
- отдельная сетевая политика склада 7;
- подтверждённый, нулевой и неизвестный товар в пути без подмены `null` нулём;
- предупреждения backend без скрытия.

### Сценарии аналитики ФОЛІО

Сценарий schema v4 хранит склады, период, условия товара, условия движения,
параметры расчёта, сортировку и выбранную вкладку. Новый сценарий можно
сохранить только после успешного `capabilities` для совместимых снимков v4.
Старые сценарии читаются через ограниченное преобразование; неподдержанные
условия не придумываются и не отправляются.

## Важные правила отображения

- фильтры движения меняют показатели периода, но не текущий остаток;
- totals и ratios всегда берутся из backend;
- `currentSuppliers`, поставщики подтверждённого транзита и менеджер продаж —
  разные сущности;
- `sellerCodes` не используется;
- `MIN=0`, сетевой запрет склада 7 и ограничение MAX показываются отдельно;
- транзит участвует в планировании только при
  `CONFIRMED_SUPPLIER_ORIGIN`, `supplierOriginConfirmed=true` и непустом
  `availableForPlanningQuantity`;
- `NO_IN_TRANSIT_STOCK` является подтверждённым нулём, остальные неизвестные
  состояния — не ноль;
- предупреждение `RETURN_COGS_NOT_AVAILABLE` не позволяет называть показатель
  чистой прибылью после возвратов.

## Пока не является рабочей функцией

Не показывать и не отправлять как рабочие фильтры: бренд, менеджер продаж,
дополнительные штрихкоды, склады-источник/получатель перемещения, lead time,
открытые заказы поставщику, XYZ и подневный stockout. Финальное рекомендуемое
количество закупки backend пока не рассчитывает.

## Проверка после деплоя

1. Открыть «Товарна аналітика ФОЛІО» и выбрать совместимые склады v4.
2. Убедиться, что старый/неполный снимок даёт объяснимую ошибку, а не пустой отчёт.
3. Найти контрольный SKU по основному GTIN.
4. Проверить `INCLUDE` и `EXCLUDE` для группы, поставщика и вида операции.
5. Проверить неизменность текущего остатка после фильтра движения.
6. Сверить totals при нескольких складах с ответом Java.
7. Проверить отдельные состояния: сетевой запрет, подтверждённый транзит,
   смешанное или неизвестное происхождение транзита.
8. Перейти на следующую страницу и убедиться, что используется `nextCursor`.
9. Создать, применить, изменить и архивировать сценарий v4.
10. Вручную сверить минимум 10 SKU: остаток, поставщик, GTIN, продажи, валовую
    прибыль, MIN/MAX и товар в пути.

Пункты 3–10 требуют задеплоенной Java schema v4 и актуальных production-like
снимков; локальный PHP-код сам эти данные не создаёт.
