# ФОЛІО: постоянная диагностика отрицательного хронологического остатка

Статус: реализовано в текущем Java worktree и поддержано WordPress frontend;
Java-изменение ещё требуется оформить отдельным коммитом и задеплоить. Проверено
по коду обоих репозиториев: 2026-09-07.

## Проблема

Java уже вычисляет первое движение, после которого хронологический остаток SKU
становится отрицательным. В ответе native preview/range присутствуют документ,
дата, количество до и после операции и величина дефицита. Однако
`folio_product_snapshot_item.last_error` хранит только короткий текст. После
завершения кампании страница состояния `FAILED` поэтому не может восстановить
подробности.

Это не причина останавливать склад или очередь. Проблемный SKU остаётся `FAILED`,
пропускается, а безопасные товары продолжают обрабатываться.

## Требуемое изменение Java

Использовать существующую таблицу MariaDB
`folio_accounting_price_diagnostic` из миграции V14 как общий постоянный журнал
диагностики учётных цен. Новая таблица не требуется.

При каждом подтверждённом `NEGATIVE_CHRONOLOGICAL_STOCK`:

1. До удаления предупреждения из ограниченного status-ответа сохранить отдельную
   строку журнала для SKU.
2. Заполнить `error_code=NEGATIVE_CHRONOLOGICAL_STOCK` и полный
   `diagnostics_json`.
3. Для apply оставить SKU в `FAILED`, очистить `applied_digest` и записать в
   `last_error` код, краткое сообщение и `jobId`.
4. Ошибка записи журнала не должна проходить незаметно: вернуть отдельную
   системную ошибку `NEGATIVE_STOCK_DIAGNOSTIC_NOT_PERSISTED` с `committed=false`.
5. Не менять данные ФОЛІО и не помечать этот SKU `VERIFIED`.
6. Продолжить обработку остальных SKU.

Для совместимости можно обобщить `recordArithmeticFailure(...)` до
`recordSkuFailureDiagnostic(...)`. Уникальность V14 по job, базе, складу, SKU и
preview/apply подходит и для этой ошибки.

## Граница достоверности

`operation` является доказанным первым движением, на котором расчётный остаток
стал отрицательным. Java не должна автоматически утверждать, что именно этот
документ ошибочен: бизнес-причиной также может быть отсутствующий или поздний
приход, неверная дата, склад либо количество в более раннем документе.

В ответе следует различать:

- `triggerMovementConfirmed=true` — проблемный момент хронологии подтверждён;
- `businessRootCauseConfirmed=false` — первопричина требует проверки оператором;
- `recommendation` — проверить указанное движение и предшествующие приходы по SKU.

## Приёмка

1. Preview SKU с отрицательной хронологией возвращает подробное предупреждение и
   создаёт строку журнала с `preview_only=1`.
2. Apply пропускает SKU, продолжает пакет и создаёт строку с `preview_only=0`.
3. После нового snapshot SKU остаётся `FAILED`, а журнал сохраняется.
4. Все нулевые количества присутствуют в JSON.
5. Повторная публикация одного job/SKU идемпотентно обновляет ту же строку.
6. Ограничение массива warnings не ограничивает количество строк журнала.
7. WordPress-запрос по базе, складу и точному SKU возвращает сохранённую запись.

## Frontend

WordPress читает последний журнал для каждой строки `FAILED` и раскрывает его под
`Остання помилка`. Отдельный журнал по складу поддерживает фильтр точного SKU и CSV.
Старые записи, созданные до этого изменения, содержат только `last_error`; для них
полная диагностика появляется после нового безопасного preview или apply.
