# Проверка отчёта «Баланс с клиентом»: БОНД АНН

Дата проверки: 2026-08-13.

Документ предназначен для совместной передачи frontend- и Java-командам. Проверка выполнена сравнением:

- PDF, сформированного кабинетом клиента;
- JSON ответа `GET /admin/folio/customer-balance`;
- штатной выгрузки 7-го отчёта ФОЛИО;
- формул Excel-шаблона `7Й чистый.xls`;
- текущего Java- и WordPress-кода.

## Краткий вывод

В отчёте одновременно есть:

1. **критическая ошибка Java API** — перевёрнут знак банковских и кассовых платежей;
2. **ошибка серверной сортировки** — платежи одного дня оказываются после накладных;
3. **ошибка сериализации/отображения дат** — даты показаны как `2026,8,13`;
4. **ошибки печатного оформления frontend**;
5. сумма **«На відстрочці / реалізації: 3 354,12 грн» тоже рассчитана неправильно**: у этих накладных нет маркера `111` в поле «Основание».

До исправления Java API отчёт нельзя показывать клиенту как финансово правильный.

## 1. Ошибочная отсрочка: должно быть 0,00 грн

Дата состояния отчёта:

```text
13.08.2026
```

API ошибочно включил в отсрочку шесть расходных накладных только потому, что их контрольный срок позже даты отчёта:

| Документ | Основание | Контрольный срок | Сумма, грн |
|---|---|---:|---:|
| `777414` | `555053Woo o ...` | 14.08.2026 | 1 687,27 |
| `777413` | `555055Woo o ...` | 14.08.2026 | 156,91 |
| `777466` | `555057Woo o ...` | 15.08.2026 | 192,66 |
| `777467` | `555058Woo o ...` | 15.08.2026 | 175,99 |
| `777475` | `555054Woo o ...` | 14.08.2026 | 965,30 |
| `777465` | `555059Woo o ...` | 15.08.2026 | 175,99 |
| **Итого** | | | **3 354,12** |

Проверка суммы:

```text
1 687,27
+ 156,91
+ 192,66
+ 175,99
+ 965,30
+ 175,99
= 3 354,12
```

Арифметически API сложил эти строки в `3 354,12`, но бизнес-классификация неверна: ни одно основание не начинается с `111`.

Правильные поля ответа:

```json
{
  "deferredAmount": 0.00,
  "overdueDeferredAmount": 0.00
}
```

### Важное правило отсрочки

Отсрочка существует только при одновременном выполнении двух условий:

```text
basis начинается с "111"
и controlDate > asOfDate
```

Для корректной отсрочки в ФОЛИО обязательны одновременно:

- будущий `SCL_NAKL.CONTRLDATE`;
- основание с маркером `111`.

Одна будущая `controlDate` без `111` не является отсрочкой. В обычных накладных контрольная дата не является контролируемым бизнес-полем и не должна уменьшать сумму «К оплате».

Старый Excel-шаблон технически суммирует такие будущие даты и поэтому также может показать ложные `3 354,12`. Это дефект формулы шаблона, а не подтверждение бизнес-отсрочки. По инструкции поле «Основание» и маркер `111` обязательны.

После исправления Java frontend должен использовать готовые поля backend:

```text
row.deferred
row.overdueDeferred
row.deferredAmount
row.overdueDeferredAmount
```

Frontend не должен постоянно дублировать формулу Java. Однако до исправления API комбинация `deferred=true` при `basis`, не начинающемся с `111`, является диагностическим признаком дефекта backend и такой отчёт нельзя показывать клиенту.

## 2. Критическая ошибка Java: знак платежей

PDF и JSON показывают:

| Показатель | Получено | Правильно по ФОЛИО |
|---|---:|---:|
| Остаток на начало | −9 284,98 | −9 284,98 |
| Расход по накладным | 50 897,35 | 50 897,35 |
| Оплата через банк | **−26 586,12** | **26 586,12** |
| Оплата через кассу | **−15 026,31** | **15 026,31** |
| Общий долг | **83 224,80** | **−0,06** |

Правильная формула:

```text
commonDebt = openingBalance
             + expenseTotal
             - receiptTotal
             - bankPaymentTotal
             - cashPaymentTotal

commonDebt = -9 284,98
             + 50 897,35
             - 0,00
             - 26 586,12
             - 15 026,31
           = -0,06
```

Сейчас Java получает отрицательные сырые значения платежей, оставляет их отрицательными и затем вычитает:

```text
- (-26 586,12)
- (-15 026,31)
```

Из-за этого платежи ошибочно увеличивают задолженность.

### Где исправлять

Ошибка находится в Java, в `FolioCustomerBalanceService.mapAmounts()`.

Сейчас:

```java
row.rawBankPayment(),
row.rawCashPayment()
```

Для текущего результата `I_DOLG_DOC` должно быть:

```java
row.rawBankPayment().negate(),
row.rawCashPayment().negate()
```

Использовать именно `negate()`, а не `abs()`, чтобы сохранить противоположное направление возвратного/исходящего платежа.

Регрессия появилась в Java-коммите:

```text
876c50c fix(folio): align customer balance with Folio report
```

Frontend не должен самостоятельно менять знак платежей: после исправления Java это приведёт к повторному перевороту знака.

## 3. Правильные итоговые значения

После исправления знаков backend должен вернуть:

```json
{
  "openingBalance": -9284.98,
  "expenseTotal": 50897.35,
  "receiptTotal": 0.00,
  "bankPaymentTotal": 26586.12,
  "cashPaymentTotal": 15026.31,
  "commonDebt": -0.06,
  "deferredAmount": 0.00,
  "overdueDeferredAmount": 0.00,
  "prepaymentAmount": 0.00,
  "payableNow": -0.06
}
```

Расчёт суммы «К оплате» по принятой формуле:

```text
payableNow = commonDebt - deferredAmount + prepaymentAmount
payableNow = -0,06 - 0,00 + 0,00
           = -0,06
```

Отрицательное значение нельзя заменять нулём или модулем. В данном случае `−0,06` — практически нулевое сальдо/небольшая переплата, а не долг клиента.

`prepaymentAmount = 0` для проверенного набора данных корректен: в рассматриваемых платежах нет примечаний, начинающихся с `222`.

## 4. Ошибка порядка строк в Java

Штатный 7-й отчёт ставит платежи перед накладными того же календарного дня.

Например, 07.07.2026:

1. кассовый платёж №277;
2. кассовый платёж №274;
3. расходные накладные этого дня.

В PDF сначала показаны накладные, затем платежи. Из-за этого `balanceBefore` и `balanceAfter` не совпадают с привычной сверкой ФОЛИО, даже после исправления итоговой суммы.

Текущая Java-сортировка сначала сравнивает полный `LocalDateTime`, включая время, и только потом тип строки:

```java
.comparing(RawRow::documentDate, ...)
.thenComparingInt(row -> isPaymentRow(row) ? 0 : 1)
```

Нужно:

1. сравнивать календарную дату без времени;
2. внутри даты ставить платёж перед накладной;
3. затем сохранять `sourceOrder`.

Принцип:

```java
.comparing(row -> toDate(row.documentDate()), ...)
.thenComparingInt(row -> isPaymentRow(row) ? 0 : 1)
.thenComparingInt(RawRow::sourceOrder)
```

Unit-тест должен использовать строки одного дня с разным временем. Текущий тест с `00:00:00` не обнаруживает эту ошибку.

Кроме того, существующий тест классификации сейчас закрепляет неправильное правило: строка с будущей контрольной датой и пустым `basis` ожидается как `deferred=true`. Этот тест необходимо изменить и добавить два отдельных случая:

```text
будущая дата + basis без 111 → deferred=false
будущая дата + basis с 111  → deferred=true
```

Frontend не должен сортировать `rows`: порядок влияет на последовательные `balanceBefore`/`balanceAfter` и обязан приходить правильным с Java.

## 5. Ошибка дат

PDF показывает даты так:

```text
2026,8,13
2026,7,10
2026,7,7
```

Java фактически вернула `LocalDate` массивами:

```json
[2026, 8, 13]
```

А frontend-функция `dateText()` понимает только строку:

```text
2026-08-13
```

### Правильное долговременное исправление

Java должна сериализовать все даты этого DTO как ISO-строки:

```json
"2026-08-13"
```

Нужно отключить timestamp/array-сериализацию `LocalDate` или явно задать формат `yyyy-MM-dd` для:

- `filters.dateFrom`;
- `filters.dateTo`;
- `filters.asOfDate`;
- `row.controlDate`;
- `row.documentDate`;
- `row.invoiceDate`.

Frontend временно может поддерживать оба формата:

```text
"2026-08-13"
[2026, 8, 13]
```

После нормализации показывать:

```text
13.08.2026
```

Frontend не должен превращать ISO-день в локальный `Date` через UTC с возможным сдвигом календарной даты.

## 6. Ошибки печатного frontend-вида

### 6.1. Не печатаются цвета

В PDF отсутствует привычная цветовая схема Excel, хотя экранный CSS задаёт цвета.

В print CSS требуется:

```css
.pc-folio-balance,
.pc-folio-balance * {
    -webkit-print-color-adjust: exact !important;
    print-color-adjust: exact !important;
}
```

Должны сохраняться:

- голубой итоговый блок;
- светло-жёлтая действующая отсрочка;
- красная просрочка;
- зелёная предоплата;
- ярко-жёлтая сумма «К оплате».

### 6.2. Заголовок таблицы не повторяется

На страницах 2 и 3 отсутствуют названия 14 колонок.

Добавить:

```css
@media print {
    thead {
        display: table-header-group;
    }
}
```

### 6.3. Пустая четвёртая страница

PDF содержит полностью пустую страницу 4. Вероятная причина — абсолютное позиционирование корневого отчёта в print CSS:

```css
.pc-folio-balance {
    position: absolute;
}
```

Для печати использовать нормальный поток:

```css
.pc-folio-balance {
    position: static;
}
```

После изменения повторно проверить Safari Print Preview и отсутствие лишнего page overflow.

### 6.4. Не показаны период и склады

В печатном заголовке должны присутствовать:

```text
Период: 07.07.2026 — 13.08.2026
Склады: Все склады
Состояние на: 13.08.2026
```

Значения брать из `response.filters`, а не из часов браузера.

## 7. Что frontend уже сделал правильно

- показал десять итоговых показателей;
- сохранил 14 основных колонок;
- использует отдельные поля `summary`, не пересчитывая их самостоятельно;
- не потерял отрицательные значения;
- предусмотрел классы для начальной строки, отсрочки, просрочки и предоплаты;
- вызывает Java через серверный WordPress proxy, не раскрывая Java API напрямую браузеру.

Основная неверная сумма не является результатом frontend-формулы: frontend честно отобразил ошибочный Java response.

## 8. Порядок исправления

### Java — обязательно сначала

1. Вернуть `negate()` для `rawBankPayment` и `rawCashPayment`.
2. Считать `deferred=true` только когда `basis` начинается с `111` **и** `controlDate > asOfDate`.
3. Считать `overdueDeferred=true`, когда `basis` начинается с `111`, но действующей будущей отсрочки уже нет.
4. Исправить сортировку: календарная дата → платёж перед накладной → `sourceOrder`.
5. Возвращать `LocalDate` строкой `yyyy-MM-dd`.
6. Добавить регрессионный тест по данным БОНД АНН либо обезличенному эквиваленту: будущая дата без `111` не является отсрочкой.
7. Пересобрать и развернуть Java API.

### Frontend — после нового Java response

1. Временно поддержать строку и массив даты.
2. Исправить print colors.
3. Повторять `<thead>` на каждой печатной странице.
4. Убрать пустую страницу.
5. Добавить период, склады и дату состояния.

## 9. Контроль после исправления

Отчёт считается исправленным, если:

- банк показывает `26 586,12`, без минуса;
- касса показывает `15 026,31`, без минуса;
- общий долг равен `−0,06`;
- действующая отсрочка равна `0,00`;
- просроченная отсрочка равна `0,00`;
- предоплата равна `0,00`;
- «К оплате» равно `−0,06`;
- платежи одного дня расположены перед накладными;
- все даты показаны как `dd.MM.yyyy`;
- страницы 2 и 3 имеют заголовок таблицы;
- пустой четвёртой страницы нет;
- цветовая схема сохраняется в PDF.
