# Скорость KREUL: аудит и план ускорения

Проверено: 2026-09-14, production `kreul.com.ua`, гостевые GET-запросы,
HTML публичных страниц, DOM браузера, read-only WP-CLI и локальный исходный код.
Аудит для владельца сайта и разработчика. Исходный замер — 14.09.2026.
**Обновлено 17.09.2026:** новое меню опубликовано на production, WPB отключён.
Сокращение HTML и времени ответа подтверждено повторными замерами. Обнаружена
регрессия общего кэша ссылок меню; следующая задача — исправить её с сохранением
ускорения. Остальные исправления не внедрены. Подробности — в разделе
[«Повторный production-аудит 17.09.2026»](#повторный-production-аудит-17092026).

## Подтверждённые проблемы

### 1. Огромное дерево категорий на каждой проверенной странице

**Статус на 17.09:** проблема объёма дерева устранена на проверенных production
страницах; полная приёмка ограничена обнаруженной регрессией ссылок общего кэша.
Описание ниже — исходная проблема и первоначальная постановка.

На главной примерно **618 687 байт** приходится на виджет бокового меню:
около **81% HTML**. Во всём исходном HTML 7 884 стартовых элемента и 3 325 ссылок.
В DOM работающего браузера подтверждено **3 278 ссылок внутри меню**;
после работы скриптов общее число элементов выросло до 8 748.

Владелец: `wpb-accordion-menu-or-category`, виджет
`widget_wpb_wmca_accordion_widget`, размещённый в правой колонке.
Локальный код также содержит неограниченный обход категорий (`depth => 0`) в
[shortcode](../wp-content/plugins/wpb-accordion-menu-or-category/inc/wpb-wmca-shortcodes.php).
Отдельный read-only CLI-профиль `dynamic_sidebar('sidebar-1')` на production
подтвердил **4,7393 с**, **619 830 байт**, **1 дополнительный SQL-запрос** для
боковой колонки. Это не изолированный таймер одного widget и не обычный HTTP
request: контекст страницы отсутствует, `SAVEQUERIES` включён только в этом
процессе. Нельзя прибавлять этот результат к HTTP TTFB или считать его точным
временем каждого реального открытия. Размер HTML и серверные затраты делают
меню первым кандидатом для исправления.

**Сделать:** показывать корневые категории и текущую ветку; остальные дочерние
ветки получать по раскрытию. На странице входа и в оформлении заказа полный
каталог заменить компактной ссылкой. Новую реализацию разместить в собственном
`paint-shop-ux`, сторонний plugin не редактировать. Сохранять обычные ссылки
на категории и доступную навигацию с клавиатуры; дочерние категории должны быть
доступны и со страниц родителей. Кэшировать дерево/ветку с ключом языка и
сбрасывать кэш при изменении категорий; если выводятся количества товаров,
учесть обновления состава каталога и синхронизации.

**Приёмка:** начальная разметка меню ≤50 КБ, ориентир ≤200 ссылок на типовой
странице, все ветки доступны, активная ветка видна, корректны мобильный экран
и переключение языка. Простое скрытие дерева через CSS размер HTML не уменьшит.

### 2. HTML передаётся без сжатия

Запросы с `curl --compressed` получили тело прежнего размера и заголовки без
`Content-Encoding`. Сервер отвечает как Apache. Локальный расчёт gzip level 6
для сохранённых ответов:

| Страница | Исходный HTML | gzip, расчёт |
|---|---:|---:|
| Главная | 767 674 | 97 412 |
| Категория | 759 201 | 96 451 |
| Вход | 719 053 | 89 944 |

Расчёт для главной — примерно **87% меньше передаваемого HTML**. Это не означает
ускорение всей страницы на 87%: ожидание PHP и изображения остаются.

**Сделать:** проверить доступность `mod_deflate` и включить gzip для публичного
HTML, CSS, JS, SVG и JSON в конфигурации владельца веб-сервера. Проверить
`Content-Encoding: gzip` и `Vary: Accept-Encoding`; отдельно проверить политику
сжатия авторизованных ответов. Пример директивы для review администратора:

```apache
AddOutputFilterByType DEFLATE text/html text/plain text/css text/javascript application/javascript application/json image/svg+xml
```

Это пример, не готовый deploy: нужны проверка модуля, действующего virtual host,
синтаксиса и текущих правил. Перед изменением сохранить конфигурацию; при ошибках
восстановить её и выполнить штатную перечитку конфигурации.
Источник: [документация Apache mod_deflate](https://httpd.apache.org/docs/2.4/mod/mod_deflate.html).

### 3. Каталог сам перезагружает страницу

В [psu-force-per-page.php](../wp-content/mu-plugins/psu-force-per-page.php)
после измерения колонок записываются cookies и вызывается `location.reload()`
(строка 143). Этот скрипт присутствует в production HTML категории.
Вызов зависит от cookies/sessionStorage; фактическое удвоение запроса в свежем
мобильном браузере ещё нужно записать в Network.

**Сделать:** сохранить одно стабильное число товаров на странице, а колонки
адаптировать через CSS. Изменение числа товаров — только явным действием клиента
или на следующем переходе, без reload после первой отрисовки и resize.
Согласовать два действующих параметра `pp` и `per_page`, пагинацию и фильтры.

**Приёмка:** один запрос документа на открытие каталога с чистыми cookies;
resize не загружает документ повторно; страницы 2+ и фильтры сохраняют результаты.

### 4. Файлы склада получают новую версию каждую секунду

В production HTML один и тот же `stock-locations-for-woocommerce/js/common.js`
имел версии `1789388559` и `1789388732` на двух запросах главной.
Причина подтверждена локальным кодом: `enqueue_frontend()` использует `time()`
для CSS/JS. Меняется URL неизменного файла; браузер обычно запрашивает его заново.

**Сделать:** в собственном compatibility-коде заменить версии только известных
SLW handles на версию plugin/`filemtime`. Не менять сторонний plugin напрямую.
Проверить дублирование blockUI: WooCommerce и SLW подключают разные копии.
Удалять дубль только после проверки зависимостей и событий корзины.

**Приёмка:** при последовательных переходах URL неизменных файлов совпадают;
повторная загрузка идёт из browser cache либо через корректную revalidation;
после обновления файла версия меняется. Работают выбор склада и корзина.

### 5. Общие страницы загружают функциональность импорта заказов

На гостевой главной обнаружены 19 внешних script-тегов и 13 stylesheet-тегов.
Среди них `pcoe.js`, два скрипта WP Social, скрипты аккордеона и две копии blockUI.
Сами по себе эти количества не доказывают вклад каждого plugin в задержку.

В [Ui.php](../wp-content/plugins/pc-order-import-export/inc/Ui.php),
метод `enqueue_js()` подключает JS/CSS без проверки страницы.

**Сделать:** привязать ресурсы PCOE к страницам/виджетам, где используется импорт,
черновик или соответствующая панель; сначала составить их полный список.
Аналогично проверить область подключения WP Social и складских ресурсов.
Маркетинговые и административные плагины оценивать по профилю, не отключать пачкой.

**Приёмка:** гостевая главная не получает ресурсы функций, которых на ней нет;
импорт, быстрый заказ, работа менеджера, авторизация и корзина проходят smoke-check.

## Кэш и база: что уже работает

Read-only production WP-CLI подтвердил:

- внешний object cache используется, Redis connected;
- `WP_CACHE=true`, `WP_DEBUG=false`, постоянный `SAVEQUERIES` не включён;
- autoload options — 362 138 байт;
- Action Scheduler: 3 390 complete, 21 pending, 6 failed на момент проверки;
- `DISABLE_WP_CRON` не определён; наличие системного планировщика не проверено.

В отдельном CLI-профиле bootstrap занял 3,5754 с: 17 SQL-запросов суммарно
0,0059 с. Это указывает на необходимость профиля PHP/hooks/cache/HTTP-вызовов,
а не на доказанную медленную SQL-базу. CLI не воспроизводит PHP-FPM/Apache
и OPcache обычного веб-запроса; вывод о конкретном виновнике пока не сделан.

Эти данные не подтверждают массовый backlog или проблему большого autoload.
Причины шести failed-заданий и просрочку pending следует изучить отдельно.
Установка ещё одного Redis plugin не является первым шагом.

**Нужно проверить:** полный page cache. В списке drop-ins виден `object-cache.php`,
дополнительный CLI-read подтвердил отсутствие `advanced-cache.php`;
в HTTP-ответах нет признака cache HIT. Это не исключает серверный кэш.
Один `WP_CACHE=true` не доказывает кэширование HTML — см.
[WordPress wp-config](https://developer.wordpress.org/advanced-administration/wordpress/wp-config/).

**План:** после облегчения меню проверить и настроить один page cache для
публичных GET-страниц. Исключить вошедших пользователей, корзину, checkout,
кабинет, AJAX/REST и изменяющие состояние URL. Учитывать язык, cookies склада,
пагинацию и фильтры. Предусмотреть сброс после синхронизации товаров, цен и остатков.
Оптовые цены и содержимое чужой корзины не должны попадать в общий кэш.
Источник: [правила кэширования WooCommerce](https://developer.woocommerce.com/docs/best-practices/performance/configuring-caching-plugins).

## Порядок внедрения

| Очередь | Работа | Результат и критерий |
|---|---|---|
| 1 | Сжатие + компактное дерево категорий | Меню ≤50 КБ; публичный HTML передаётся с gzip; число ссылок существенно снижено |
| 2 | Убрать автоматический reload; стабилизировать SLW URLs | Один document request; файлы повторно используются браузером |
| 3 | Условная загрузка JS/CSS; проверить page cache | Меньше ненужных ресурсов; доказанный HIT/BYPASS по нужным сценариям |
| 4 | Профиль динамических сценариев | Найдены конкретные медленные PHP hooks, SQL или обращения Java для каждого действия |
| 5 | Исправить подтверждённые причины в корзине/кабинете/отчётах | Повторные замеры тех же действий и контроль корректности данных |

Первые три шага затрагивают общий путь загрузки и поэтому имеют приоритет.
Для динамики отдельно измерять поиск по SKU/названию, фильтры складов, товар,
корзины на 1/20/100 строк, пересчёт доставки, вкладки документов и отчётов.
Роли: гость, розница, опт, менеджер. Не размещать заказы и не выполнять реальные
платежи/фискализацию ради теста скорости.

Для каждого сценария снять 5–10 последовательных замеров до/после, одинаковые
данные и роль; холодный/тёплый browser cache и page cache отмечать отдельно.
В динамических запросах разложить время на WordPress bootstrap, hooks, SQL,
HTTP к Java и рендер. Для Java/ФОЛИО использовать профильные skills после
подтверждения, что задержка действительно в этом слое.

Предварительные цели, **не обещанный результат**: тёплый гостевой TTFB ≤0,8 с,
обычная динамическая страница ≤1,5 с, LCP ≤2,5 с в согласованных условиях.
Тяжёлые отчёты получают отдельный бюджет времени и статус фонового выполнения.

Каждую группу исправлений принимать отдельно, сохранять возможность точечного
отката кода/конфигурации и повторять проверки цен, остатков, корзины и ролей.
Политика deployment: [регламент проекта](BOOTSTRAP_AND_RECOVERY.md).
Оптовые изменения одновременно отражать в каноне и коде справки по
[DOCUMENTATION_POLICY.md](DOCUMENTATION_POLICY.md).

### Методика и ограничения сравнения

- 20 последовательных гостевых HTTPS GET: по 5 запросов главной, категории,
  входа и одной порции REST-ветки. Между запросами пауза 1 с; параллельной нагрузки нет.

тел: главная 38 150 байт, категория 38 681, вход 28 599, REST 1 203.
Это возможное сокращение трафика, не измеренный выигрыш времени.

Для входа: `Cache-Control: no-cache, must-revalidate, max-age=0, private`.
Для REST: `Cache-Control: no-store`, `Vary: Origin`. Для главной/категории нет
наблюдаемого `Age`/cache-HIT; это не доказывает отсутствие всех серверных кэшей.
Redis и его конфигурация повторно не профилировались; значения раздела выше
остаются наблюдениями 14.09. В коде нового меню есть серверный transient-кэш.

SLW всё ещё отдаёт новые версии неизменных файлов на каждом запросе (`time()`).
В HTML остаются ресурсы импорта заказов и две копии blockUI; количество тегов
не равно количеству фактических сетевых запросов и не доказывает их время.

### Автоматическая перезагрузка осталась

В гостевом HTML главной и категории присутствует скрипт `psufp_applied` с
`location.reload()`, на странице входа именно этот скрипт отсутствует.
В существующей авторизованной вкладке категории изменение ширины на **390 px**
без команды reload вызвало переход через пустой документ; после этого серверная
версия SLW script изменилась с `1789661455` на `1789661571`.
Это наблюдение повторной загрузки, согласующееся с resize handler в
`psu-force-per-page.php`. Точный счёт document/asset requests через Network
в текущем инструменте не снят. Заявлять отсутствие лишнего reload нельзя.
Ширина восстановлена, временная вкладка закрыта; ошибок browser console не было.

### Новая регрессия: общий кэш сохраняет ссылки «Быстрого заказа»

**Подтверждено до любых новых изменений:** в гостевом HTML главной и категории
корневые ссылки меню, а также публичный REST `parent=0`, содержат, например:

```text
/shvydke-zamovlennia/?cat=rasprodaza
/shvydke-zamovlennia/?cat=aerografia
```

При этом активная «Фарби акрилові» ведёт на обычную категорию. Такая же смесь
наблюдается в авторизованном DOM. Отдельный гостевой GET первой ссылки вернул
HTTP 200 и сообщение **«Недостатньо прав для швидкого замовлення.»** вместо каталога.
Это пользовательская ошибка навигации, а не утечка закрытых данных.

**Причина по коду:** `PSU_Category_Menu::node()` сохраняет результат
`get_term_link()` в общий branch transient. Ключ учитывает locale/config/parent,
но не контекст страницы. На странице `[pc_quick_order]` два существующих фильтра
`term_link` в `pc-wholesale-quick-order.php` и child theme переписывают URL на
quick-order. После прогрева этой страницы изменённый URL становится общим для
обычных страниц и REST до обновления namespace/истечения TTL. Содержимое кэша
на production не очищалось и искусственно не перепрогревалось для доказательства;
наблюдаемое направление ссылок и этот путь кода достаточны для постановки бага.

Отсутствие private data в DTO не делает URL независимым от контекста. Поэтому
пункт 1 принят **по сокращению объёма/времени**, но не по полной корректности
навигации. Исправление регрессии приоритетнее следующего общего ускорения.

### Одна следующая задача: контекст ссылок быстрого меню без потери кэша

**Статус: постановка; реализация не разрешена этим аудитом.** Начать только после
отдельного решения пользователя, сначала на `paint.local`.

**Цель:** сохранить достигнутые размеры и скорость меню, исключив переходы гостя
из обычного каталога в недоступный «Быстрый заказ» и зависимость ссылок от того,
какая страница первой заполнила кэш.

**Владелец и файлы:**

- `paint-shop-ux/inc/category-menu.php`: `key()`, `node()`, `branch()`, REST/renderer;
- `paint-shop-ux/assets/category-menu.js`: только если нужен явный публичный
  контекст подгружаемой ветки;
- `wp-content/mu-plugins/pc-wholesale-quick-order.php` и
  `wp-content/themes/generatepress-child/functions.php`: владельцы двух текущих
  фильтров `term_link`; согласовать применение, не отключать всё глобально;
- tests/README владельца, оптовая инструкция и справка при изменении пути клиента.

**Подход:** общий кэш должен хранить нейтральные данные категории. Конечный URL
строить в явном контексте «каталог» / «быстрый заказ» после чтения кэша либо
разделить представления по строго ограниченному контексту с корректной передачей
его в REST. Просто добавить текущий request URI в ключ недостаточно: REST имеет
другой URI, а произвольные варианты породят лишние копии. Не отключать кэш и не
возвращать полный walker. Перевести существующие contextual filters на совместимый
контракт; исключить повторный rewrite. Канонические ссылки не получать через
слепое глобальное удаление чужих фильтров. При будущем rollout сменить только
namespace/version меню, чтобы прежние ошибочные URL перестали использоваться.

**Приёмка:**

1. На локальном сайте воспроизвести обе очередности прогрева: быстрый заказ →
   гостевой каталог/REST и каталог/REST → быстрый заказ. Гостевые home/category/REST
   всегда дают обычные ссылки категорий; разрешённый быстрый заказ сохраняет свой
   ожидаемый переход. То же для ещё не раскрытых веток и «Ще категорії».
2. Проверить гостя, розницу, опт и менеджера; UA/RU, desktop/mobile 390 px,
   активную глубокую ветку, отсутствие JS, переходы и повторное раскрытие.
   Все настройки/роли/категории получать из окружения, без production IDs.
3. Объём начального меню остаётся ≤50 КБ, обычная порция REST ≤30 строк,
   полная скрытая копия taxonomy не возникает. Сохранены дедупликация запросов,
   сортировка, активная ветка и инвалидизация после taxonomy changes.
4. Семь сопоставимых локальных GET/renderer-замеров до/после, отдельно первый и
   тёплые вызовы. Ориентир: медиана не хуже исходной более чем на 10%; при выходе
   сначала повторить сопоставимую серию и определить причину. Это критерий,
   не обещание дополнительного ускорения. Не сравнивать локальные секунды с
   production-таблицей и не сбрасывать общий production cache.
5. Регрессионный тест должен падать на текущем коде именно из-за смешения URL
   после изменения контекста; затем PHP/JS проверки и browser smoke.

**Границы:** без исправления reload/gzip/SLW в том же diff, без заказов, оплаты,
Java/ФОЛИО apply, новых плагинов и автоматического production deploy.

**Откат:** локально вернуть только патч этой задачи, сохранив native widget 1.3.0
и его настройки; после смены формата кэша использовать новый namespace при
включении и откате. На production откат этой правки тоже вернёт известный дефект,
поэтому решение принимает владелец; WPB заново автоматически не включать.

## Следующий этап: стабильные SLW resources, локально 17.09.2026

Владелец сообщил о deploy предыдущих исправлений меню/пагинации и разрешил
реализацию следующего этапа только локально. Read-only production smoke меню
зафиксирован в [отчёте меню](CATEGORY_MENU_LOCAL_VERIFICATION_2026-09-15.md): новых
дефектов не найдено, WPB неактивен, загружается category-menu 1.3.1. Ниже относится
только к новой локальной Paint Shop UX 1.3.2; на production её не публиковали.

### Причина и изменение

Stock Locations 3.2.1 ставит `time()` в версии неизменных frontend ресурсов.
До правки два последовательных перехода главная → категория дали разные URL
четырёх одинаковых файлов и повторную передачу всех тел.

Собственный `paint-shop-ux/inc/slw-assets.php` фильтрует только URL известных
ресурсов: `ver` = версия SLW + content hash. Чужие handles/пути/CDN, admin и
нечитаемые файлы пропускаются. Vendor не изменён. Зависимости, порядок, placement
и inline/localized stock data не перерегистрируются. Полный inventory из восьми
handles и точечный откат находятся в [README владельца](../wp-content/plugins/paint-shop-ux/README.md).

### Измеренный результат браузера

Обычный браузер с включённым кешем, без route interception и hard reload. На
реальные локальные страницы временно добавлен read-only footer probe, который
выводит `PerformanceResourceTiming`; данные читались из DOM. Probe не меняет
ресурсы или cache headers и удалён после приёмки. Перед правкой: главная, затем
категория; после: главная с новой версией, затем категория с теми же версиями.

| Общий ресурс | Повторный переход до, transferSize | Повторный переход после, transferSize |
|---|---:|---:|
| frontend-style.css | 1 596 | 300 |
| common-style.css | 448 | 300 |
| common.js | 1 111 | 300 |
| jquery.blockUI.js | 6 891 | 300 |
| **Сумма, байт** | **10 046** | **1 200** |

До: четыре полные передачи, сжатое содержимое 8 846 байт суммарно. После:
четыре revalidation, без повторных тел. `transferSize` учитывает заголовки
условными 300 байтами браузера, это не физический сетевой захват. Для blockUI
дополнительно проверен реальный conditional HTTP GET: **304, тело 0 байт**.
Первое посещение после правки закономерно передало те же 10 046 байт.

В карточке подключаются также underscore-min.js и product.js: первое получение
этих двух новых ресурсов — 7 794 + 4 688 байт transferSize. При следующем открытии
карточки все шесть SLW ресурсов дали по 300 байт (сумма 1 800), без повторной
полной передачи. URL и содержимое файлов совпадают; новых JS errors нет.

Все проверенные локальные заголовки: gzip, ETag/Last-Modified,
`Cache-Control: no-cache, public, must-revalidate, proxy-revalidate`. Поэтому
нулевые сетевые запросы или memory-cache без revalidation не заявляются.
Конфигурация Local/nginx не менялась. Стабильные URL создают условия для кеширования;
частота повторных проверок определяется сервером. Выигрыш TTFB/LCP полного сайта
и результат на production из этих данных не следуют.
