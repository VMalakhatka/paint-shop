# Аналитика покупателей KREUL

Проверено: 2026-10-11. Владелец WordPress-кода: `lavka-customer-analytics`.
Владелец кабинета GA4 и политики обработки данных должен быть подтверждён владельцем
магазина. Источники: настройки production, разрешённые scoped изменения Google,
Woo CRUD-агрегаты, собственный код и локальные тесты. **Файлы нового модуля есть на рабочем сайте, но модуль
не активирован и сбор через него не включён.**

## Что есть и что подготовлено

Подтверждено на production 2026-10-11: после пользовательского подтверждения OAuth
в Rank Math восстановлены существующие account/property/stream, а не создан новый
ресурс. GA4 `G-2CCYP21JKC` — ресурс `510945322`, поток Website `12366203570`.
Это наблюдаемые идентификаторы production, не переносимые defaults. Счётчик
присутствует в публичном HTML; сохранены `install_code=true` и прежнее
`exclude_loggedin=true`. Woo order attribution включена. Новый consent/ecommerce
модуль по-прежнему **не включён**.

Доступ к отчётам GA4 подтверждён в браузере и API: чтение агрегатов за
04–10.10.2026 и штатный sample-запрос Rank Math возвращают данные. История уже была
в Google; пустая локальная база Rank Math не означает отсутствие истории GA4.
Ручное получение данных Rank Math запущено, завершение импорта не подтверждено.

Search Console: 11.10.2026 после отдельного явного разрешения владельца магазина
владение URL-prefix ресурсом `https://kreul.com.ua/` подтверждено для текущего
Google-аккаунта. Google показал «Право собственности подтверждено автоматически»,
способ — Google Аналитика. Затем, по отдельному явному разрешению того же владельца,
установлен дополнительный HTML meta через Rank Math → Инструменты веб-мастера →
Google Search Console. Google подтвердил оба способа; новый аккаунт/доступ не добавлен.
Публичная главная отвечает 200 и содержит один meta с сохранённым значением.
Предыдущая ошибка site access 403 устранена: Search Analytics API возвращает успех
без строк за 04–10.10.2026. Обзор Google доступен, но сообщает, что данные
обрабатываются и следует повторить проверку приблизительно через день. Это не
доказательство отсутствия поискового трафика. Тест Rank Math показывает
«Підключено» для Search Console и Analytics; cache import пока остаётся в состоянии
«Триває отримання», Cached Days/Data Rows = 0. Повторный импорт не запускался.

Источники проверки: UI production Rank Math, выборочная проверка WordPress options
без OAuth tokens, API Google Analytics Admin/Data и Search Console, публичный HTML.
Проверка одного счётчика на главной не заменяет аудит всех страниц и рекламных тегов.

Подготовлен отдельный модуль с согласием и событиями витрины. Точный event contract,
storage, queue limits и rollback:
[README владельца](../wp-content/plugins/lavka-customer-analytics/README.md).
События Google отправляются только браузером после согласия. Серверный платёжный
callback записывает подтверждающий marker Woo, но не отправляет событие в Google.
Возвраты, server-side delivery и сверка с банковскими документами ещё не реализованы.
Google ecommerce-события и consent mode основаны на
[документации GA4](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce)
и [basic consent](https://developers.google.com/tag-platform/security/guides/consent).

### Дополнительное подтверждение и проект политики — 11.10.2026

Разрешённая production операция была ограничена одним полем `google_verify` в
option **`rank-math-options-general`** (имя с дефисами, не подчёркиваниями).
До сохранения создан закрытый snapshot этой группы с mode 0600 в серверном temporary
directory; нет активной ecosystem операции. После UI submit проверены persisted
значение, публичный meta и успех Google «Тег HTML — Успешно подтверждено».
SHA-256 остальных полей этой группы и Analytics options не изменились. Код подтверждения,
Google email и OAuth tokens не копируются в Git/документы. DNS, файлы в корне и
права другого аккаунта не менялись. Temporary snapshot не является долговечной
резервной копией; перед будущим изменением нужен новый закрытый снимок.

HTML proof не зависит от установки Analytics snippet/analytics consent, но зависит
от сохранения поля и вывода `rank_math/head`. Не отключать весь Rank Math или этот
meta ради подавления аналитики. Selective rollback: после нового разрешения вернуть
только прежний `google_verify` из закрытого snapshot через штатное поле/option API,
не всю группу и не всю БД; затем проверить HTML и состояние Google. Удаление meta
может отменить дополнительное подтверждение, поэтому обычный rollout его сохраняет.

На этапе HTML verification подготовлен **неопубликованный проект политики v0.1**: украинский текст для покупателей
и русская страница решений владельца. Воспроизводимый источник:
[`build-privacy-policy-draft.py`](../scripts/build-privacy-policy-draft.py).
Генератор только создаёт локальный DOCX в игнорируемом `outputs/`, не пишет в WordPress.
В нём явно отмечены незаполненные юридическое имя/адрес/контакт, фактические получатели,
сроки заказов/логов/backup и решение GA4 retention (2/14 месяцев и reset-on-activity).
180 дней — срок выбора согласия подготовленного модуля, не всех cookies сайта.
На этом историческом этапе GA4 работал по прежней конфигурации: утверждение «только после
согласия» описывает целевую схему и не публикуется до network-проверки всех тегов.
Источник юридической сверки: [закон Украины](https://zakon.rada.gov.ua/laws/show/2297-17),
технических сроков: [Google retention](https://support.google.com/analytics/answer/7667196?hl=en).
Проект требует решения владельца и юридической проверки; сам по себе не разрешает
публикацию/новый сбор. На окончание этого этапа `active=false`, `enabled=false`;
страница политики, настройки GA4, импорты, заказы и платежи не изменялись. Последующие
разрешённые настройки Google указаны ниже; v0.1 не является текущей редакцией.

### Согласованные сроки и подготовка запуска — 11.10.2026

Владелец подтвердил предложенные сроки и дал команду начать. Это не разрешение
пакетно удалять заказы, отправлять рассылки, проводить реальные платежи или переносить
в production всю рабочую копию. Полученные реквизиты и контакт владельца находятся
только в игнорируемом частном проекте политики v0.5, не в Git. WayForPay/Checkbox
пока заявлены как готовящиеся к запуску, а не как уже работающие сервисы. Для будущей
подписки выбран email; ни сбор подписок, ни рекламные рассылки не включены.

Разрешённые изменения Google проверены свежим GET после одного PATCH:

| Настройка | До | После / время UTC |
|---|---|---|
| `eventDataRetention` | `TWO_MONTHS` | `FOURTEEN_MONTHS`, 14:09:09 |
| `resetUserDataOnNewActivity` | true | false, 14:09:09 |
| Enhanced measurement | Все семь флагов true | Все семь false, 14:13:34 |

Семь флагов: `pageChangesEnabled`, `siteSearchEnabled`, `formInteractionsEnabled`,
`outboundClicksEnabled`, `fileDownloadsEnabled`, `videoEngagementEnabled`, `scrollsEnabled`.
Так исключаются автоматические несогласованные URL/поисковые/формовые события и
дубли собственного event contract. Google может не возвращать default-valued false;
проверка требует успешного чтения ожидаемого resource name, затем нормализует эти
семь полей. Master `streamEnabled` и список search query parameters не менялись.
Основной Rank Math snippet ещё установлен; отключённые enhanced события **не означают**
site-wide consent. Новый модуль по-прежнему inactive/enabled=false.
Срок GA4 не ограничивает все стандартные агрегированные отчёты и не означает
восстановление старых уже удалённых данных.

Перед каждой записью создан закрытый mode-0600 snapshot лишь выбранных прежних
полей/несекретных идентификаторов в серверном temp directory. Он не является
долговечной резервной копией. OAuth/customer data не экспортировались. WordPress
options, privacy page, application files, заказы и платежи на этом этапе не менялись.
При первоначальном lock операция остановилась до записи; lock другой задачи
не очищался. Повторный запуск только после отсутствия lock. Общий deploy не запускался.

Согласованные организационные сроки — решения, а не подтверждение внедрения:

- Обращения без покупки: 12 месяцев после закрытия, с отдельными правилами для споров/заказов.
- Необязательная attribution заказа: 14 месяцев; только отдельные аналитические поля,
  не заказ, чек или обязательные сведения.
- Неактивные кабинеты: пересмотр через 24 месяца; перед возможным удалением
  уведомление за 30 дней и проверка незавершённых операций/обязательств.
- Обычные access logs: 30 дней; платёжные/фискальные/инцидентные журналы отдельно.
- Операционные backup сайта: ротация до 90 дней, отдельно обязательные архивы;
  после восстановления повторно применяются удаления/отзывы.
- Будущий email: до отзыва, максимум 24 месяца с подписки/нового явного подтверждения;
  отдельный обоснованный срок минимальных доказательств согласия/отказов до запуска.
- Analytics-choice cookie: 180 дней предусмотрены выключенным модулем.

Woo retention options при чтении пусты. Автоматическое удаление/анонимизация не
настроены; сроки log/backup фактически ещё не проверены. Обязательные финансовые
документы требуют перечня от бухгалтера, а не произвольного единого срока.
Нельзя публиковать обещание уже действующего удаления/consent, пока оно не проверено.

Оператор: [`configure-analytics-google.php`](../scripts/configure-analytics-google.php).
По умолчанию preview. Указать подтверждённый `LCA_EXPECTED_MEASUREMENT_ID` и
`LCA_CONFIG_KIND=retention` либо `enhanced`; `LCA_CONFIG_APPLY=1` — только после
отдельного разрешения на соответствующую production запись. Пример без записи:

```bash
LCA_EXPECTED_MEASUREMENT_ID=G-EXAMPLE123 LCA_CONFIG_KIND=retention wp eval-file scripts/configure-analytics-google.php
```

Скрипт сверяет выбранный measurement ID и resource name, не очищает ecosystem lock,
не выводит token, сохраняет closed snapshot до PATCH, меняет только конечный updateMask.
При timeout сначала GET; повторной автоматической записи нет. `outcome_unknown`
не является успехом. GET клиента может штатно обновить OAuth token. Scoped rollback
требует нового решения и чтения прежних полей: не восстанавливать всю группу/БД.
Сокращение GA retention может привести к удалению истории, поэтому автоматического
отката 14 → 2 месяца нет. Enhanced rollback возвращает только прежние семь флагов,
не master switch или список search parameters.
Локальные fake API tests: `php scripts/tests/analytics-google-config.php` — 12 cases;
preview, idempotency/default false, stream mismatch, empty resource, locks,
single PATCH/readback, 403, timeout и неизвестный исход, отсутствие token в output.
Primary contract: [retention PATCH](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1alpha/properties/updateDataRetentionSettings),
[enhanced measurement fields](https://developers.google.com/analytics/devguides/config/admin/v1/rest/v1alpha/EnhancedMeasurementSettings).

До полного запуска открыты: фактическое cookie/recipient/log/backup inventory,
финансовые сроки, завершение/утверждение политики, живые guest/mobile/wholesale
network и DebugView tests, custom dimensions, точечное включение и приёмка событий.
Тестовый реальный платёж не разрешён этой подготовкой. Разграничивать `purchase`
(оформление) и `payment_confirmed` (маркер оплаты, с ограничениями browser delivery).

### Скрипт предпусковой проверки

Скрипт проверки читает последние семь полных календарных дат, рассчитанных по UTC
(отчёт GA4 использует timezone ресурса); выводит только флаги, checksum и агрегаты
eventName/eventCount. Не выводит tokens, customer rows или тексты приватных страниц.
Выбор stream учитывает legacy key Rank Math `view_id`. Пример безопасного запуска:
`wp eval-file scripts/audit-analytics-release.php`. Перед переносом в другой environment
перепроверить доступность Rank Math API и выбранные property/stream.

## Найти существующий кабинет

1. В админке открыть Rank Math SEO → Analytics → Settings/подключение Google.
   Посмотреть, какой Google-аккаунт и ресурс выбраны. Не отключать связь и не создавать
   новый ресурс до проверки, чтобы сохранить историю.
2. Войти этим аккаунтом на [Google Analytics](https://analytics.google.com/), найти
   ресурс сайта и поток с указанным measurement ID.
3. Администратор ресурса предоставляет оператору права редактора через Access management.
   Для проверки отчётов достаточно просмотра, для настроек нужны соответствующие права.
   Пароли, OAuth tokens и экспорт секретных Rank Math options в чат не отправлять.
4. Если аккаунт принадлежит бывшему подрядчику, запросить передачу доступа.
   Новый ресурс — отдельное решение владельца, не автоматическая замена старого.

### Восстановить соединение Rank Math без смены ресурса

1. До переподключения сохранить закрытый снимок несекретных выбранных settings:
   account/property/view (stream)/measurement ID, `install_code`, `exclude_loggedin`,
   Search Console URL. OAuth options и авторизационные URL в Git/чат не копировать.
   Проверить отсутствие активного импорта и выбрать время без параллельного изменения
   этих settings. При работающем импорте не повторять запуск вслепую.
2. Нажать «Тестові підключення» и дождаться результата. Зелёный исходный индикатор
   или сохранённая связь не доказывают успешного чтения отчётов.
3. При необходимости открыть «Перепідключення»; выбор аккаунта и новые/расширенные
   права подтверждает человек. После OAuth повторно выбрать прежние сайт, ресурс и
   поток: переподключение может очистить selections/options. Сверять measurement ID
   и URI, а не только display name: на этой проверке три ресурса назывались P - GA4.
4. Сохранить прежнюю политику установки кода и исключения пользователей. Не создавать
   новый GA4 ресурс/stream, не отключать другие integration plugins и не удалять данные.
   Затем сохранить, обновить страницу и отдельно проверить реальные API-запросы.
5. Если GA4 работает, а Search Console отвечает 403 и кабинет не даёт доступа к сайту,
   не повторять OAuth: получить site access/ownership отдельным решением. Возможность
   верификации через существующий GA4 tag требует прав Edit и проверки условий Google:
   [подтверждение владения](https://support.google.com/webmasters/answer/9008080?hl=en).
   На production 11.10.2026 с отдельным разрешением владельца сработала автоматическая
   верификация через Google Аналитику. Google требует не удалять gtag.js для сохранения
   этого подтверждения и рекомендует дополнительный способ. Перед заменой/подавлением
   Rank Math snippet подтвердить независимый способ владения (HTML tag/file либо DNS)
   отдельной согласованной операцией и проверить его в Google. Иначе будущий consent
   rollout может поставить сохранение текущего подтверждения под риск; это риск,
   а не наблюдаемая потеря доступа. На production дополнительный HTML tag уже
   подтверждён 11.10.2026, регламент сохранения указан выше. Не ослаблять согласие
   ради проверки Google.
6. «Оновити дані вручну» запускает cache import. «Триває отримання» — progress, не
   успех. Проверить законченный job, Cached Days/Data Rows и доступный отчёт после
   обновления страницы. Ошибку прав не лечить удалением кэша.

Восстановление конфигурации: вернуть только выбранные несекретные settings через
эту же страницу и проверить persisted values/публичный tag; не откатывать всю БД,
заказы или OAuth tokens. Откат Git не отменяет WordPress options. При ошибке после
сохранения сначала перечитать значения, а не автоматически повторять submit.

Ограничение текущей установки: Rank Math с `exclude_loggedin=true` по умолчанию
исключает все вошедшие роли, включая клиентов. Не выключать это вслепую: нужно
отдельно исключить сотрудников, проверить приватные кабинетные URL и согласие.
Собственный модуль уже предусматривает такой отбор, но его release gates остаются
обязательными. Наличие работающего GA4 tag ещё не доказывает ecommerce, воронку
заказ → подтверждённая оплата и корректное измерение оптовиков.

## Выпуск: обязательные ворота

1. Подтвердить GA4 доступ. Проверить старые ecommerce-теги, GTM и Google/TikTok/Pinterest
   integrations. Оставить одного владельца GA4 событий. Модуль подавляет только
   Rank Math snippet; он не заменяет site-wide consent для всех рекламных сервисов.
   До подавления этого snippet обеспечить независимое подтверждение Search Console
   согласно регламенту выше; на production дополнительный HTML способ уже проверен,
   его meta должен сохраняться независимо от Analytics tag.
2. Опубликовать/проверить privacy policy и согласовать конкретный состав данных,
   срок хранения и права оператора. Модуль использует псевдонимные cookies GA4,
   не обещать полную анонимность. Отказ не блокирует покупки.
3. В потоке GA4 проверить enhanced measurement. Автоматические page views, search
   и form interactions могут дублировать события или передавать URL/текст формы.
   До включения отключить конфликтующие автоматические события и проверить реальные
   network payloads. На production семь флагов уже выключены 11.10.2026; проверка
   payloads и unwanted referrals платёжных провайдеров остаётся обязательной.
4. Получить отдельное решение владельца на production deploy/activation/enablement.
   Manifest `manual`. Deploy dry-run тоже может делать git pull/подготовку и до
   такого решения не запускался. Полная локальная БД на production не переносится.
5. После разрешённого code deploy активировать plugin. Активация без настройки
   `lca_settings` остаётся выключенной. Настройку пишет администратор через WordPress
   option API/операторский WP-CLI, без токенов:

   ```bash
   wp option update lca_settings '{"enabled":false,"measurement_id":"G-EXAMPLE123","debug":false}' --format=json
   wp plugin activate lavka-customer-analytics
   ```

   `G-EXAMPLE123` — placeholder, заменить подтверждённым потоком. Только после пунктов
   1–4 и проверки конфигурации отдельно изменить `enabled` на `true`. Debug использовать
   для контролируемого теста, затем выключить. Новый production option не создавался.
6. Под клиентской, не административной сессией пройти сценарии в DebugView и Network:
   отказ → ни одного Google запроса от модуля; согласие → один tag; отзыв → события
   остановлены; посетитель без доступа не получает данные чужого заказа.
7. Отдельно пройти обычный каталог, фильтр/поиск с пустой выдачей, быстрый оптовый
   заказ, импорт, повтор документа, изменение/удаление количества, checkout error,
   unsplit/split receipt и реальную интеграцию callback. Реальный платёж не запускать
   как тест без отдельного разрешения. Локальные fixtures не заменяют эти проверки.
8. Зарегистрировать нужные event-scoped custom dimensions: `customer_segment`,
   `filter_set`, `payment_state`, `search_empty`, `result_count`, `error_type`.
   Не регистрировать transaction_id как высококардинальную custom dimension.
9. Создать воронку: карточка → корзина → begin_checkout → purchase;
   отдельно payment_confirmed, в разрезе источника и device category. Сравнивать один
   период и одну популяцию с согласием. Purchase означает оформлено, не оплачено.

## Повторяемый анализ заказов

Read-only инвентаризация, без вывода секретов/контактов:

```bash
wp eval-file scripts/audit-customer-analytics.php
```

Обезличенная аналитика Woo, default период 01.07–10.10.2026; для нового отчёта всегда
передать явный период. Без формирования/изменения заказов или ФОЛИО:

```bash
LCA_REPORT_FROM=2026-09-01 LCA_REPORT_TO=2026-09-30 wp eval-file scripts/analyze-customer-sales.php
```

Скрипт читает максимум 5000 строк, постранично по 100, иначе останавливается с ошибкой
и требует меньшего периода. При удалённом read-only запуске из stdin WP-CLI `eval-file`
в restricted shell может не поддерживать `/dev/stdin`/`php://stdin`; допустим
`wp eval 'eval(substr(stream_get_contents(STDIN), 5));'` с **проверенным PHP-файлом**.
Файл не сохраняется на сервере. Не исполнять непроверенный внешний код.

### Определения и контроль

- Группа = исходный заказ и его дочерние счета. Суммируются дети **или** исходный
  unsplit, никогда оба. Отдельно считать родителей вне периода и draft-only группы.
- Товарный спрос: processing/completed/on-hold, за вычетом возвратов; refunded не
  даёт оставшихся товарных позиций. Pending/failed/cancelled исключены. On-hold может
  быть нехваткой: это не доказательство отгрузки. Общая сумма заказа включает его
  условия доставки/налога; item value — line total без налога, минус refund.
- Тестовые/сотруднические строки не попадают в рейтинг товаров/пар. Сводка показывает
  сотрудников отдельно. Старые роли — **текущие**, не исторические; новые checkout
  snapshots фиксируют segment на дату. Wholesale — тип клиента сайта, не offline канал.
- Для совместных покупок один SKU считается один раз на группу, сегменты разделены.
  Корзины >80 SKU исключены из перебора пар, число исключений видно. Пары с 1–4
  совпадениями — только гипотезы; даже 5 совпадений не доказывают полезность набора.
- Валюты не суммировать. Mixed-currency group отдельно помечается. Отчёт не делает
  валютную конвертацию. Утраченные товарные карточки сохраняют числовой fallback.
- Источник/устройство берутся из сохранённого `_lca_*`, иначе Woo attribution.
  Нативные `(direct)`/`source_type=typein` означают direct, `source_type=admin` —
  создание из админки. Не классифицировать их как отсутствие источника. Заказы из
  админки не являются шагами посетителя и не входят в browser conversion.
  Неизвестный источник не заменяется «SEO» или «прямым». Region — код billing country/state,
  не IP-география, не город посещения и не выбранный склад.
- Ни processing, ни автоматически заполненный date_paid не подтверждают денег.
  Старый gateway transaction marker требует сверки. Новый payment_complete marker —
  свидетельство Woo hook, не независимая банковская выписка. Без достаточных данных
  показывать «не подтверждено», а не нулевые реальные оплаты.
- Без трафика GA4 нельзя вычислить конверсию устройства, потерянные корзины,
  последовательность посещений или вклад SEO. Отменённые заказы не заменяют потери
  checkout. Отчёт Woo не включает продажи физических магазинов без Woo-заказа.

## Задания персоналу после подключения

Продакт-менеджер: проверить 10 пар из отчёта — совместимость, задача пользователя,
дополнительный инструмент/расходник, остаток и маржа. Пара разных фасовок не обязательно
набор. Для 3 подходящих задач подготовить комплектацию, фильтры и статью с товарами.
Оптовые многотоварные заказы не выдавать за предпочтения конечного потребителя.

Менеджер розницы: еженедельно сверять товары, просмотр → добавление → заказ,
нулевой поиск, тип устройства, отказ/ошибки checkout. Для каждого проблемного товара
фиксировать одну проверяемую причину (описание, цена, наличие, доставка) и задание.
Не пересчитывать site conversion только по числу заказов с устройства.

Администратор/аналитик: контроль одного tag, согласия, PII, purchase deduplication,
callback coverage и расхождения GA4/Woo. Для каждого расхождения проверить split,
роль сотрудника, блокировщики, согласие, возврат и отсутствие return страницы.
Расписание/автоматизация не создавались, периодический отчёт пока запускается вручную.

## Rollback и остаточные этапы

Выключить `lca_settings.enabled` через option API или деактивировать только этот
plugin. Другие настройки и заказы не откатывать. Runtime Rank Math override прекращается:
его старый persisted snippet снова станет действовать, поэтому решение об этом
счётчике/согласии принимать явно. Cookies покупателей не очистятся одним server deploy;
очистка выполняется браузером при отзыве. Order metadata не удаляется.

Локальная активация с реальным enabled=false выполнена. HPOS hooks, in-memory
checkout metadata, UK/RU и синтетический consent/desktop/mobile проверены.
Канон оптовой инструкции обновлён, опубликованная справка обновлена **в коде**.
Production-страница после deploy не проверялась. Чтение GA4 отчётов подтверждено
11.10.2026; Search Console site ownership подтверждено в тот же день через GA4,
чтение API доступно. Готовность отчётов Search Console и завершение cache import
Rank Math ещё не подтверждены. Независимый HTML способ подтверждения уже проверен
и должен сохраняться при consent rollout. DebugView, privacy approval, tag inventory,
организационное соблюдение сроков, deploy dry-run, production
enablement и живые сценарии остаются открытыми.
