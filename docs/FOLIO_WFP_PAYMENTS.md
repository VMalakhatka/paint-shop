# Автоматический банковский приход после WayForPay

Проверено 2026-10-16. Код: `pc-wayforpay-checkbox` **0.2.0** и Java
`folio.payment`. Реализовано и проверено локально/в rollback-лаборатории;
**production-деплой, журнал MSSQL и включение автоматики ещё не выполнены**.

## Что именно записывается

Проверенное серверное уведомление WayForPay `Approved / 1100` → отдельная очередь
→ один банковский приход ФОЛИО на всю оплаченную сумму, склад **5**.
Вид операции **МАЛАФОП**, тип **РЕАЛИЗАЦИЯ**, учитываемый документ, сумма учитывается
в долгах. Комиссия WayForPay не вычитается из оплаты покупателя.

Решение владельца: приход **не зависит от счёта**. Счёта может ещё не быть; их
может быть несколько; сумма может покрывать лишь часть счёта; счёт может меняться
или уйти в архив. Всё это не мешает учесть полученные деньги. Первоначально сумма
не распределена по счетам (`NOTOVAROST=SUM_POR`, `NACLAD_POR=0`), строки оплаты
товаров не создаются. Распределение выполняется отдельно в ФОЛИО. Этот поток сам
по себе не помечает счёт полностью оплаченным и не выпускает ручной чек по накладной.

Плательщик — привязка покупателя к ФОЛИО **на момент первого подтверждённого
Approved**, включая штатного «Интернет клиента». Ключ сохраняется вместе с
проверенным событием до вызова `payment_complete`. Позднее переназначение профиля
не меняет существующий приход. Имя Java получает по сохранённому ключу ФОЛИО.
Если нет ни привязки, ни настроенного штатного клиента, событие сохраняется для
review — случайного плательщика программа не выбирает.

Уведомление о возврате не стирает приход: подтверждённое поступление сохраняется,
а отдельный банковский расход требует проверки. **Автоматического расхода пока нет.**
Подтверждение оплаты и возвращённая сумма не должны исчезать из учётного следа.

Checkbox, создание счетов и банковский приход — независимые результаты оплаты.
Ошибка чека, отсутствие счёта или split не блокируют очередь прихода. Повтор
прихода не вызывает callback, `payment_complete`, создание счёта или новый чек.

## Настройки WordPress

Только защищённый конфиг сервера, не Git и не поля страницы. URL Java берётся из
существующих `lts_options.java_base_url` / `base_url`. Новый выделенный токен
хранится отдельно от обычного токена Java. Для HTTP нужен закрытый доверенный
канал; предпочтителен HTTPS. Redirect при запросе с токеном запрещён.

| Константа | Назначение |
|---|---|
| `PC_WFP_FOLIO_MODE` | `off` по умолчанию; `preview` только проверка; `live` запись |
| `PC_WFP_FOLIO_START_AT` | Новый фиксированный момент запуска UTC; обязателен при включении |
| `PC_WFP_FOLIO_SOURCE_SCOPE` | Устойчивая идентичность сайта, одинаковая с Java |
| `PC_WFP_FOLIO_API_TOKEN` | Выделенный случайный секрет, минимум 32 символа; одинаковый с Java |
| `PC_WFP_FOLIO_PAUSED` | Строго `true`: сохранять новые намерения, не обращаться к API |

Существующий проверяющий callback адаптер должен оставаться включённым:
`PC_WFP_CHECKBOX_MODE=live` и подтверждённый `PC_WFP_MERCHANT_MODE=live` для
боевых приходов. `PC_WFP_CHECKBOX_PAUSED=true` останавливает только чек, не приход.
Режим видимости WayForPay отдельным покупателям не является sandbox.

Безопасный исходный набор (секрет/идентичность/границу запуска оператор задаёт отдельно):

```php
define('PC_WFP_FOLIO_MODE', 'off');
define('PC_WFP_FOLIO_PAUSED', true);
```

Точные свойства Java и HTTP-контракт: Java-репозиторий,
`docs/api/FOLIO_WFP_PAYMENTS_API.md`. Требуются отдельные `api-enabled` и
`apply-enabled`, точная БД, scope, merchant hash, cutoff и проверенный технический
ID банковского шаблона. Исторический ID шаблона не является переносимым default.

## Хранение и защита от дублей

- WordPress: `pc_wfp_receipts.folio_payer_key/approved_at` — неизменяемая привязка
  и время подтверждения; `pc_wfp_folio_payments` — отдельная очередь, команда,
  хеш, режим, попытки, флаг отправки, refund, ID/номер результата.
- Схема WP обновляется версионно при загрузке плагина под отдельной блокировкой;
  activation также устанавливает её. Версия `pc_wfp_folio_schema=2`.
- ФОЛИО: `LAVKA_WFP_PAYMENTS` — постоянный журнал, уникальный ключ
  `SHA256(scope|merchantHash|reference)` и хеш неизменяемой команды. Журнал и
  штатный приход сохраняются **одной транзакцией MSSQL**.
- Журнал MSSQL устанавливается только отдельной согласованной миграцией.
  HTTP/старт Java ничего не создаёт в схеме ФОЛИО.
- Возврат callback и worker используют общую блокировку заказа. Action Scheduler
  выполняет `pc_wfp_folio_payment`; каждые 5 минут sweep восстанавливает доставку
  намерений, если запуск отдельного задания потерялся. Группа `pc-wfp-folio`.
- До отправки apply сохраняется `sent=1`. После потери ответа только GET по тому
  же ключу. Даже 404 не разрешает повторный POST. Не сбрасывать sent, не удалять
  журнал и не менять ключ ради повторной записи.

Две даты различаются: UTC первого сохранённого Approved и дата банковского
документа в `Europe/Kyiv`. Повтор обработки не переносит платёж на сегодняшний день.
Старые записи без нового снимка подтверждения не подхватываются. Backfill отсутствует.

## Где смотреть и как восстанавливать

Администратор с `manage_woocommerce`: WooCommerce → заказ → **Банковский приход ФОЛИО**.
Там отдельный статус, номер и безопасный код причины. Успех также добавляет заметку
заказа. В действиях заказа — **Сверить / возобновить банковский приход ФОЛИО**.
Штатная форма Woo проверяет nonce; обработчик повторно проверяет права и блокировку.

| Статус | Что делать |
|---|---|
| `QUEUED` | Ожидать очередь; до 12 попыток, задержка до часа |
| `PREVIEW` | Проверка без записи; не превращается автоматически в live |
| `RECONCILE` | Результат отправки уточняется по прежнему ключу; не вводить второй приход |
| `SUCCEEDED` | Сверить номер, сумму, плательщика и склад 5 в ФОЛИО |
| `REVIEW` | Проверить причину/журнал; кнопка не стирает ключ, snapshot или sent |
| `REFUND_REVIEW` | Приход сохранён, нужен отдельный учёт возврата денег |

Типовые причины: `payment_payer_missing` — сохранённый ключ отсутствует в ФОЛИО;
`bank_template_required` — банковский шаблон не соответствует правилам;
`payer_or_template_changed` — данные изменились между preview и apply;
`folio_unknown_outcome_not_found` — нет подтверждённого результата после попытки;
`folio_mode_changed` — очередь нельзя переводить из preview/test в live;
`existing_payment_requires_review` — найден приход с этим reference вне журнала;
`folio_attempt_limit` — исчерпаны фоновые попытки.

После отправленного apply кнопка делает только сверку. Для подтверждённого rollback
и нового apply нужен отдельный операторский разбор; автоматического снятия защиты нет.
Не менять плательщика задним числом через профиль пользователя.

## Включение: отдельный production-этап

1. Подтвердить восстановимую копию, reviewed bank template, область запуска и
   закрытый доступ к Java. Проверить отсутствие предыдущих приходов для теста.
2. Отдельно установить согласованную DDL журнала и права SELECT/INSERT на него.
   Сохранить hash миграции; не переносить полную локальную БД на production.
3. Развернуть Java и WP 0.2.0. Проверить WP schema version 2, доступность Action
   Scheduler и журнал MSSQL. Не включать live до готовности обоих компонентов.
4. Настроить секреты и идентичность. Проверить Java status/preview под авторизацией,
   оставляя apply выключенным. Preview не вызывает native INSERT_PLAT.
5. Для проверки preview использовать **новый** заказ; это всё равно реальная
   оплата WayForPay, а не симуляция. Старый PREVIEW не продвигается в live.
6. После отдельного разрешения включить Java apply, WP live и снять WP pause.
   Поставить новую фиксированную границу начала в обоих компонентах; не переносить
   её назад для ранее проведённой вручную оплаты.
7. Один новый согласованный платёж: Woo-намерение → один банковский приход →
   журнал → GET того же ключа. В ФОЛИО сверить плательщика, сумму, дату, склад5,
   нераспределённый остаток и отчёт долга; отдельно проверить Checkbox.

Откат: `PC_WFP_FOLIO_PAUSED=true`, Java `apply-enabled=false`; оставить API status
доступным для сверки. Не удалять очереди/журнал/приходы и не запускать полный DB deploy.

## Что проверено и что ещё нет

- Подпись/подделка callback, повтор, split/no-invoice, неизменяемый плательщик,
  crash до outbox, потеря ответа после commit, GET-only recovery, refund, capability,
  pause, preview/off — offline PHP-тесты.
- Java auth, общий с PHP хеш, guards, атомарный service workflow, rollback при
  ошибке журнала и возврат прежнего результата — unit-тесты.
- В локальном WordPress таблица устанавливается; две реальные DB-сессии
  подтверждают общую блокировку. Финансовые API локально не вызывались.
- Paint_Rus: native приход4 без счёта, остаток4, склад5, аллокаций0, успешный
  rollback и отдельное подтверждение отсутствия тестовых сущностей. Доказательства
  и ограничения — в Java API-документе и lab SQL.
- Не выполнены: production миграция/деплой, новый сквозной HTTP/live приёмочный
  платёж, проверка нового независимого прихода в настольном UI/отчёте долга,
  runtime concurrency/commit-loss через реальную Java API. Поэтому автоматика
  по умолчанию выключена. Автоматическое распределение и возврат — отдельные функции.
