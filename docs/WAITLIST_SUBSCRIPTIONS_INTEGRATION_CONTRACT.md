# Ожидание и рекомендации: аудит и контракт интеграции подписок

Дата аудита: 2026-10-17. Проверен локальный worktree на `75d34cc`.
Это проект контракта для согласования после первого этапа единого профиля,
а не реализованный API и не подтверждение актуального production-состояния.
Production, почта, ФОЛИО и настройки пилота в рамках аудита не проверялись и не менялись.
Изменения другого направления и актуальный remote main в этот срез не включены.

## 1. Границы ответственности

Единый профиль тем/брендов/категорий, его клиентский экран, отображение менеджеру
и Broadcasts принадлежат направлению кабинета менеджера. Здесь не создаётся второй
профиль и не предлагается менять их код до согласования интерфейса чтения.

Waitlist владеет явной потребностью, источниками черновиков, отложением/удалением
запроса и отдельным согласием на уведомления ожидания. Будущие рекомендации владеют
доказательством спроса по покупкам, но не могут сами подписывать клиента.
Общий сервис доставки, частотных ограничений и журнала — отдельный следующий этап;
владелец и физическое хранилище должны быть согласованы, а не созданы независимо
каждым producer.

Существующий пилот на одном настроенном клиенте остаётся обязательным ограничением
Waitlist независимо от того, скольким клиентам доступен единый профиль. Подписка
на бренд/категорию не расширяет пилот и не включает ожидание, рекомендации или канал.

### Переданный контракт первого этапа профиля

Получен 2026-10-17 от направления кабинета менеджера. В проверенном локальном
срезе `75d34cc` файла CustomerSubscriptions нет; сведения ниже — контракт handoff,
не независимая проверка исходников, миграции или production. Исходники этого
направления здесь не редактируются.

Владелец: PCOE `CustomerSubscriptions`; единственное хранилище профиля — user_meta
`_pcoe_subscriptions_v1`:

```text
{
  version: 1,
  topics: [price, arrival, news, promotion],
  scope: all | selected,
  rules: [{topic: * | price | arrival | news | promotion,
           brand: termId | 0, category: termId | 0}],
  updated_at
}
```

Это описание структуры, не JSON для записи. Формат `updated_at`, точные имена
публичных методов и обработку отсутствующего профиля следует подтвердить по
готовому сервису; не реализовывать параллельный evaluator в Waitlist.

- Внутри правила бренд AND категория, категория включает потомков; между правилами OR.
- Бренды ограничены `psu_catalog_supplier_terms(true)`, категории —
  `PSU_Category_Menu`, visible-minus-blocked. Не расширять эти справочники локальным
  перечнем терминов. Семантику нулевых ID и пустых rules подтвердить у владельца API.
- Клиент сохраняет настройки через Woo save account details; карточка менеджера read-only.
- Существующий Broadcasts `OPT_OUT` — общий запрет **маркетинга**.
- `email_enabled` Waitlist остаётся отдельным явным согласием. Topics не содержат
  ожидание или recommendations. Topic `arrival` означает маркетинговую тему,
  а не разрешение отправлять персональное уведомление ожидания.
- В первом этапе общего профиля расписание и общий event-journal не реализованы;
  общих правил частоты также нет. Это не отменяет существующие собственные
  планировщик и mail_log Waitlist, описанные ниже. Фоновую рассылку Waitlist
  к этому профилю пока не подключать. Direct Waitlist consent (`email_enabled`
  и `email_consent_at`) не изменяется и автоматически не мигрируется.

### Два назначения коммуникации

| Назначение | Допуск сейчас / контракт следующего этапа |
|---|---|
| `marketing` — цены, новости, промо, общие поступления | Единый профиль тем/областей плюс отсутствие Broadcasts OPT_OUT; каналы и общий бюджет — следующий этап |
| `requested_waitlist_notice` — наличие явно запрошенного SKU/черновика | Существующие pilot gate, активная потребность, отдельное Waitlist email_enabled и почтовый master; маркетинговые темы не включают и не выключают этот запрос |
| Рекомендации по истории покупок | Будущее маркетинговое назначение, пока отдельная тема/согласие не согласованы; покупки сами не дают разрешения писать |

Отказ от маркетинга не трактуется как отказ от отдельно заказанного уведомления
ожидания; согласие на ожидание не разрешает добавлять в него рекламные позиции.
Общий технический запрет канала или явный будущий отказ «от всех сообщений» —
отдельный механизм; **не называть Broadcasts OPT_OUT таким механизмом**.
Классификация здесь продуктовая, не юридическое заключение.

## 3. Выводы и ограничения интеграции

1. CAS предотвращает конкурирующую отправку внутри Waitlist, но Broadcasts и
   рекомендации этот claim не видят. Ни общий email-флаг, ни одинаковые cron-интервалы
   не решают межмодульную дедупликацию.
2. `mail_observed` хранит состояние по product_id, без общего ID поступления.
   Cursor синхронизации — проверка свежести, не идентификатор нового поступления:
   новая синхронизация не должна разрешать повторное письмо.
3. Частота 15 минут — частота проверки; 24 часа — минимальный интервал попыток
   по товару после нового нуля. Сейчас нет общего лимита контактов, quiet hours,
   digest-режима или выбора канала.
4. Согласие содержит boolean и timestamp, но не версию текста, источник решения
   и историю отзывов. Нельзя автоматически объявить его согласием на рекомендации,
   маркетинговые поступления, Telegram или звонки.
5. После отмены claim до отправки маркер `notified` остаётся установленным.
   Отложенная общим бюджетом доставка не должна использовать этот путь как
   «успешно уведомлено»: иначе предложение потеряется. Нужен отдельный deferred.
6. Проверка непосредственно перед письмом сверяет свежесть cursor, но не повторно
   читает численный stock каждого SKU. Это остаточный race с изменением наличия;
   общий dispatcher должен повторно валидировать товарный снимок перед отправкой.
7. Первый положительный снимок не доказывает факт нового прихода. Для ожидания
   достаточно «есть в наличии»; сообщение о поступлении требует отдельного факта.
8. Hash адреса остаётся связанной с клиентом информацией. Это не анонимный журнал.

## 4. Предлагаемый контракт чтения и кандидата

Имена ниже логические; не фиксируют новые классы, таблицы или ключи общего профиля.
Единственный владелец профиля предоставляет версионированный read adapter. Producer
не читает чужой JSON напрямую и не сохраняет собственную копию брендовых подписок.

### Решение о подписке

Вход следующего этапа: customer_id, communication_class (`marketing` или
`requested_waitlist_notice`), purpose (`waitlist_availability`,
`purchase_recommendation`, `brand_arrival_news`), product_id/variation_id и
канонические brand/category IDs.

Для marketing adapter использует единственный CustomerSubscriptions и Broadcasts
OPT_OUT. Для requested_waitlist_notice он получает согласие от Waitlist, не
добавляя topic в профиль и не проверяя совпадение брендовых/категорийных правил.
Канал и общий бюджет в будущем разрешает единый dispatcher. Адреса/токены не
передаются producer и разрешаются непосредственно перед доставкой.

Предлагаемый выход: `profile_revision` (только если профиль применялся),
`policy_version`, `consent_ref`, доступные подтверждённые каналы, предпочтительный
канал, режим частоты, timezone/quiet hours, общие и тематические ограничения,
причины отказа. Отсутствующие в v1 поля не считать уже реализованными.

Допуск requested_waitlist_notice следующего этапа:

`pilot gate AND active explicit request AND waitlist consent AND channel permission
AND no applicable technical/all-messages stop AND fresh stock AND frequency budget`.

Допуск marketing следующего этапа:

`purpose consent AND profile match AND NOT Broadcasts OPT_OUT AND channel permission
AND frequency budget AND source eligibility`.

Отсутствие общего профиля само по себе не отзывает действующее согласие Waitlist.
Недоступность обязательного adapter/неизвестная версия в новом shared-потоке даёт
deferred, не allow. Legacy-пилот до переключения продолжает существующий контракт;
новый marketing-топик не становится обходом его ограничений. Менеджер не превращает
аналитическую потребность в согласие клиента.

### Кандидат уведомления

| Поле | Назначение |
|---|---|
| contract_version, producer, communication_class, purpose | Версия, назначение и происхождение; отличить запрошенное уведомление от маркетинга |
| customer_id, candidate_key | Серверный владелец; стабильный ключ логического кандидата при повторном вызове |
| product_id / variation_id | Канонический товар, не только изменяемая строка SKU |
| source_refs, source_revision | IDs запросов/строк черновика или аналитического основания; несколько причин могут относиться к одному товару |
| event_family, event_id | Каноническое событие/эпизод наличия, одинаковый для разных producers |
| requested_qty, available_qty, stock_as_of | Правдивый смысл сообщения; не резерв и не подтверждение покупки |
| not_before, expires_at | Отложенная отправка и срок повторной проверки/истечения |
| consent_ref, profile_revision, policy_version | Доказательство решения при подготовке; перед отправкой проверяются заново |
| evidence_ref, confidence, evidence_as_of | Только для рекомендаций: ссылка на основание/полноту истории, без копии чужих покупок |

Producer передаёт кандидата, а не отправляет письмо. Ответ: `queued`, `merged`,
`suppressed`, `deferred`, `rejected` с decision_id, reason и при необходимости
next_eligible_at. Повтор запроса с тем же candidate_key возвращает то же решение.
Для ещё не готового общего event_id нельзя выдумывать ID из cron-времени или UUID
отправки; в shadow фиксировать `event_identity_missing`, реальный общий поток не включать.

## 5. Дедупликация, частота и журнал

Предлагаемый порядок после проверки всех согласий:
**явное ожидание (включая черновик) → рекомендация по покупкам → общая новость о товаре**.
Неподписанная цель не может выиграть приоритет. Нельзя добавлять маркетинговую
позицию или рекламный блок в requested_waitlist_notice без самостоятельного допуска
marketing; общий claim не объединяет разные согласия. Сопутствующие основания сохраняются
как source_refs одной товарной позиции, а не превращаются в дополнительные письма.

Два разных ограничения:

- Идемпотентность producer: UNIQUE(customer_id, producer, candidate_key).
- Общий claim по товару/событию: UNIQUE(customer_id, product_id, event_family, event_id),
  без producer и channel в ключе. Email и Telegram по умолчанию не должны обходить
  дедупликацию друг друга. Для нового смыслового события дополнительно действует
  общий временной лимит контактов по товару и по клиенту.

Оба ограничения проверяются атомарно в общем сервисе. Dedup — по каждой позиции,
не только по письму: из брендового дайджеста удаляется уже покрытый SKU, остальные
позиции остаются. Текущего JSON-CAS одного producer для этого недостаточно.
Все источники должны пройти dispatcher; проверка «SELECT, потом отправить» без
уникального claim оставляет гонку. Приоритет применим до начала отправки; уже принятое
письмо низшего приоритета не разрешает немедленно послать второе высокоприоритетное.

Общее событие наличия формируется один раз по подтверждённому снимку продающих
складов, не заново каждым модулем. Ноль/положительное значение и неизвестность
различаются. Точные границы эпизода и частичного/полного прихода согласуются отдельно;
текущий пилот не повторяет сообщение при росте положительного stock.
Рекомендация с другим основанием также проверяет недавний контакт по тому же SKU.

Общая новость «большой приход бренда» без списка SKU не допускает точной товарной
дедупликации. До появления товарного состава остаются тематический и общий лимиты;
нельзя утверждать, что отсутствие SKU доказывает отсутствие пересечения. Не добавлять
такую новость к ожиданию без согласия на новости.

Настройки централизованы: предпочтительный подтверждённый канал, immediate/digest,
общий бюджет сообщений, минимальный интервал по товару, timezone/quiet hours,
срок кандидата. Числовые маркетинговые лимиты пока не согласованы; текущие 15 минут
и 24 часа не переносить как универсальный лимит. Непроверенный канал запрещён.
Telegram позже требует привязки аккаунта, звонок — отдельной цели и журнала задачи.
Автоматический fallback после неизвестной email-отправки не допускается.

Общий журнал должен сохранять decision/candidate/event IDs, customer/product IDs,
все источники, снимок политики/согласия, канал и защищённую ссылку на получателя,
товарный снимок, not_before/expiry, reason, claim/attempt/provider IDs и времена.
Статусы решения (`suppressed`, `deferred`, `expired`) отделить от транспорта
(`claimed`, `accepted`, `delivered`, `failed`, `unknown`, `cancelled`). Delivered
ставится только по подтверждению провайдера. Unknown удерживает claim; другой канал
не является способом его обойти. Заведомая ошибка до передачи может разрешать
повтор только по явной классификации и операторскому решению, не по таймеру.

Лимиты считаются общим сервисом, с учётом зарезервированных отправок. Deferred
не помечает товар уведомлённым. Claim/release и бюджет связаны транзакционно;
результат внешнего транспорта отдельный, exactly-once доставку обещать нельзя.
Доступ к журналу — по полномочию менеджера и владельцу, без секретов провайдеров
и лишних полных payload; правила архива/удаления согласуются до массового включения.

## 6. Черновики и рекомендации по покупкам

Источники ручного запроса и черновика сохраняются независимо от почтовой доставки.
В общий кандидат идут уже сгруппированные quantities; отмена email не удаляет
черновик, удаление запроса не отменяет уже оформленную покупку. `cart_added` и
`_pcoe_demand_event` не доказывают потребление.

Рекомендации пока не реализованы в проверенном коде. Основа — подтверждённые
расходные ФОЛИО/возвраты с клиентом, SKU, датой, количеством и классификацией Java;
копировать эту классификацию в PHP нельзя. Нужны покрытие истории, asOf и стабильное
сопоставление клиента/товара. Отсутствие строки в неполном снимке не означает отсутствие
покупок. Woo заменяет источник только после согласованной полноты синхронизации.

До включения рекомендаций решить погашение потребности, открытые/split-заказы,
возвраты и выбранную периодичность клиента. Аналитический score даёт основание
кандидата, а не разрешение на коммуникацию. Для пересечения с активным ожиданием
выбирать явную потребность, сохраняя аналитическую причину для менеджера.
Точные поля backend-проекции требуют отдельного согласования; MSSQL здесь не читался.

## 7. Переход без дублей и приёмка

1. После первого этапа проверить фактический CustomerSubscriptions API и семантику
   отсутствующего профиля, scope all, нулевых ID и пустых rules. Затем согласовать
   adapter профиля, цели согласия, владельца
   dispatcher, event identity, приоритет, частотные значения и архив журнала.
2. Добавить будущий adapter в shadow: только решения/сравнение, без отправки.
   Сохранить отдельный Waitlist consent и текущий pilot gate; отсутствие общего
   профиля не должно молча подписывать клиента.
3. Сопоставить старый mail_log с новым журналом. Accepted не импортировать как
   delivered; claimed/failed удержать для review. Положительные mail_observed
   перенести как уже покрытые эпизоды либо консервативное подавление, чтобы первый
   общий проход не повторил legacy-письмо. Timestamp boolean-согласия не дополнять
   выдуманной версией текста; отметить legacy provenance.
4. Переключать единственного владельца отправки через согласованный режим
   legacy/shadow/shared. До shared остановить legacy transport и убедиться, что
   незавершённых legacy-вызовов нет. Оба scheduler могут вызывать один hook,
   но не два независимых отправителя. Не запускать накопленный backlog автоматически.
5. Проверить того же пилота без изменения остатков/создания реальных документов.
   Production-этап и реальные письма — отдельное последующее решение.
6. Откат сначала отключает shared delivery. Перед legacy восстановить подавление
   для всех shared accepted/unknown; иначе оставить письма выключенными.
   Не очищать журнал или `pending` переноса ради возобновления отправки.

Обязательные сценарии изолированной приёмки:

| Сценарий | Ожидаемый результат |
|---|---|
| SKU вручную + в черновике + в рекомендации + в новости | Одна товарная позиция; все разрешённые источники видны в журнале |
| Producers/cron одновременно | Один общий атомарный claim на товар/событие |
| Смена канала после accepted/unknown | Повтор не появляется; неизвестный исход требует review |
| Отписка/смена роли/удаление запроса между enqueue и send | Повторная проверка и отмена; другие запросы не теряются |
| Broadcasts OPT_OUT / снятие темы бренда при явном SKU | Маркетинг запрещён по своей политике; отдельное согласие ожидания и сам запрос не перезаписываются |
| Выключен Waitlist email_enabled, но включён arrival | Уведомление ожидания не отправляется; маркетинговая тема не обходит отказ |
| Только Waitlist consent, нет marketing consent | В уведомлении нет добавленных рекламных позиций |
| Legacy-клиент без общего профиля | Отдельное согласие ожидания не мигрируется в маркетинговое и не теряется |
| Snooze, закрытый черновик, чужая строка заказа | Нет уведомления по исключённому источнику |
| Quiet hours/исчерпанный бюджет | Deferred без установки notified; после срока — повторная валидация |
| Unknown stock/старый снимок/растущий положительный stock | Не фабрикуется новое поступление и повторный episode |
| Частично перекрытый дайджест | Удалены дублирующие позиции, остальные сохранены |
| Crash после принятия транспортом | Unknown claim сохраняется, нет автоматического повтора/fallback |
| Миграция и откат с legacy accepted/claimed | Нет повторной доставки старой потребности |
| Профиль включён многим клиентам | Waitlist по-прежнему доступен только текущему пилоту |
