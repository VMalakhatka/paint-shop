# Поиск → фильтры → быстрый заказ → корзина

Проверено: 2026-10-08. Окружение: **paint.local**, локальные код и база.
Аудит для владельца сайта и разработчика. Эти измерения не характеризуют
скорость production и не подтверждают равенство его базы локальной копии.
Предыдущие работы и требования к переносу:
[аудит 14.09.2026](SITE_PERFORMANCE_AUDIT_2026-09-14.md).

## Результат

Первый кандидат на ускорение — проверка точных идентификаторов в поиске.
Она вызывается и для артикула, и для обычного слова; в третьем запросе подсказок
«акрил» один SELECT занял **1091 мс из 1291 мс SQL**. В фильтрах оптового клиента
аналогичная проверка заняла **997 мс**. Это подтверждённый дорогой участок,
но план выполнения и подходящий индекс ещё не исследованы.

Следом — формирование фильтров и выборка списка быстрого заказа. Изменение
количества в корзине сравнительно быстрое; сами вычисления сумм занимают
несколько миллисекунд. Обнаружена отдельная ошибка интерфейса: после мобильного
AJAX-изменения количества подпись распределения по складам может оставаться старой.

## Метод и ограничения

- 36 последовательных HTTP-запросов: по три для восьми сценариев гостя/оптового
  клиента и четырёх сценариев быстрого заказа/классической корзины.
- Дополнительно: получение формы корзины и три запроса используемого интерфейсом
  `pc_cart_update_item`. Все 40 запросов завершились успешно; проверялось содержимое
  JSON, наличие товаров, фактическое количество в корзине, а не только HTTP 200.
- Поиск: публичный артикул `KR-79406`, слово «акрил». Фильтры: то же слово,
  «Лише в наявності», цена до 1000. Быстрый заказ: один доступный простой товар,
  три добавления по одной единице. Классический пересчёт: количества 2 → 3 → 2.
- «Первый» — первый запрос данного сценария в серии, **не холодный кеш**.
  «Повтор» — медиана двух последующих запросов. Кеш базы не сбрасывался.
- Время HTTP — до получения всего HTML/JSON. CSS, JS, изображения, отрисовка,
  скорость мобильной сети и Core Web Vitals сюда не входят.
- Временный локальный профилировщик записывал суммарное PHP/SQL-время, число
  запросов, вызывающие функции пяти самых медленных запросов и время вычисления
  корзины. SQL-тексты, клиентские данные и секреты в отчёт не переносились.
  Один ранний запрос до подключения профилировщика не входит в SQL-время.
  PHP измерялся до начала завершения запроса; это не строго всё время shutdown.
- Планировщик WordPress отключался только для измеряемых запросов. Накладные
  расходы профилирования есть. Нагрузка компьютера не изолирована: контрольные
  запросы подсказок «акрил» без профилирования дали 10,29 / 7,90 / 5,79 с.
  Поэтому числа ниже — диагностический ориентир, а не стабильный SLA или оценка
  процента будущего ускорения.
- Во всех профилированных запросах зафиксировано 0 внешних обращений через
  WordPress HTTP API. Это не доказывает отсутствие других способов обращения
  или браузерных загрузок внешних ресурсов.

## Подтверждённые источники задержки

1. **Точный идентификатор.**
   [`psu_find_exact_identifier_product_ids`](../wp-content/mu-plugins/psu-search-filters.php)
   ищет точное совпадение по нескольким ключам в `postmeta`. Его вызывает
   [поиск подсказок](../wp-content/plugins/paint-shop-ux/inc/catalog-search.php)
   и основная поисковая выдача. В третьем гостевом запросе артикула этот SELECT
   занял 1651 мс, обычного слова — 1091 мс. Нельзя просто отключить проверку
   «слов»: допустимые артикулы и альтернативные идентификаторы нужно сохранить.
2. **Поиск и списки фильтров.** В третьем оптовом запросе фильтров: Relevanssi
   `relevanssi_search` — 409 мс, `relevanssi_generate_df_counts` — 384 мс;
   `psu_catalog_unit_values` — 259 мс, `psu_catalog_scoped_terms` — 113 мс.
   Около 800 запросов — общий счётчик WordPress, не число запросов только фильтра.
3. **Быстрый заказ.** В третьем открытии один `WP_Query::get_posts` занял
   1173 мс из 1232 мс SQL. Код
   [pc-wholesale-quick-order.php](../wp-content/mu-plugins/pc-wholesale-quick-order.php)
   сортирует по SKU в meta и фильтрует непустую цену. Показаны 178 ссылок страниц
   сверху и столько же снизу (356 всего). После AJAX-добавления вызывается
   `location.reload()`: клиент ждёт добавление и повторное открытие списка.
   Медианы этих отдельных ответов составляют примерно 0,48 + 1,80 с;
   сумма не является замером полного времени пользовательского действия.
4. **Корзина.** AJAX вычисление сумм: 9,59 / 5,70 / 4,37 мс.
   Основная часть PHP-времени приходится на остальную обработку WordPress;
   оптимизировать арифметику корзины по этим данным нецелесообразно.

## Проверка интерфейса

Браузер: 1280×900 и 390×844, без имитации медленной сети. Это проверка
адаптивной страницы, не физического телефона. Проверены подсказки по SKU,
результаты по названию, применение наличия/цены, отметки выбранных фильтров,
добавление из списка, изменение количества и итогов корзины.
Гостевой поиск/фильтры и оптовые сценарии проверялись раздельно.

- Подсказки и фильтры возвращают товары; активные условия видны отдельными
  метками. На мобильном экране результаты и выбранные фильтры помещаются.
- Быстрый заказ добавляет выбранную единицу на обоих размерах; после загрузки
  списка колонка «в корзине» показывает правильное количество.
- Количество и суммы корзины обновляются; на проверенных страницах ширина
  документа равна ширине доступной области, горизонтального переполнения нет.
- Ошибок/предупреждений JavaScript в журнале этой проверки не обнаружено.
  Это не проверка всех страниц и плагинов.
- **Ошибка мобильного обновления строки:** после 1 → 2 и затем отдельного
  2 → 3 сумма строки и общий итог менялись, но «Списання: Киев — …» оставалось
  прежним. На компьютере после классического обновления и перезагрузки подпись
  соответствовала количеству. В
  [pc-cart-guard.php](../wp-content/mu-plugins/pc-cart-guard.php)
  ответ `pc_cart_update_item` содержит сумму строки и итоги, а обработчик
  обновляет их и поле количества; HTML распределения складов не возвращается
  и не заменяется. Это подтверждение устаревшей подписи в интерфейсе,
  **не доказательство неправильного реального списания**. Заказы не оформлялись.

## Конкретные следующие задачи

1. **Корректность корзины:** возвращать актуальный план складов вместе с
   AJAX-ответом, обновлять его в строке. Проверить увеличение/уменьшение,
   оба склада и режимы распределения, повторную загрузку, ограничения остатков.
   Это небольшой отдельный фикс; полный reload ради обновления подписи не нужен.
2. **Первая задача по скорости — точный поиск.** Снять `EXPLAIN` указанного
   SELECT и состав существующих индексов. Сравнить lookup SKU WooCommerce и
   поиск альтернативных идентификаторов, определить безопасный способ исключить
   дорогую повторную работу. Не добавлять индекс в production без проверки
   объёма/плана/обратимой миграции. Приёмка: те же товары по SKU, штрихкоду,
   альтернативному коду, названию и пустому результату; роли сохраняют свои цены,
   склады и ограничения. Повторить тот же baseline и сравнить HTTP/SQL-время.
3. **Фильтры:** исследовать выборки единиц и поставщиков; рассмотреть кеш только
   справочных наборов с ключом области категории и инвалидированием при импорте.
   Персональные цены, остатки и готовые корзины общим кешем не покрывать.
4. **Быстрый заказ:** заменить 178 ссылок компактной пагинацией, сохранив
   текущую страницу, начало/конец, соседние страницы и переход дальше.
   Затем убрать полный reload после добавления: обновлять количество в корзине,
   доступность, выбранные количества и сообщение по подтверждённому ответу.
   Отдельно исследовать SQL выборки SKU/цены; сторонний код не редактировать.

Для каждого исправления — отдельный scoped commit и точечный откат этого commit.
Отмена кода не отменяет миграцию индекса: у неё должен быть собственный down-план.
Процент ускорения до повторных замеров не обещается. Настройка gzip/Brotli остаётся
требованием переноса на новую площадку; старый сервер здесь не настраивался.

## Очистка и границы

Использовалась временная сессия существующей локальной оптовой роли без изменения
её прав. Исходные persistent-cart meta и строка WooCommerce session сохранены
перед тестом и восстановлены с проверкой равенства. Временный токен уничтожен,
секретный файл и MU-профилировщик удалены. Рабочее поведение сайта не изменено;
коммит содержит только отчёт, обезличенные числа и ссылку из карты документации.
Production, складские остатки и заказы не изменялись; commit/push не означает деплой.
