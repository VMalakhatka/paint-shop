# Lavka Woo

Сопровождай этот сайт как связанную систему из WordPress/WooCommerce, собственных PHP-плагинов, Java API, ФОЛИО и OVH/S3. Сначала найди владельца поведения, затем меняй минимальный слой, которому оно принадлежит.

## Начало работы

1. Прочитай [source-map.md](references/source-map.md) и выбери актуальный источник истины.
2. Для задачи по коду или данным определи границу ответственности по [architecture.md](references/architecture.md).
3. Загрузи только нужный справочник:
   - таблицы, meta и options: [data-storage.md](references/data-storage.md);
   - собственные и критические внешние плагины: [plugins.md](references/plugins.md);
   - страницы, кабинет и места вывода: [pages-and-ui.md](references/pages-and-ui.md);
   - синхронизации, отчёты, медиа и регламентные действия: [operations.md](references/operations.md);
   - разработка, конфигурация, deploy и rollback: [deployment-and-configuration.md](references/deployment-and-configuration.md);
   - пользователи, цены, заказы, ФОЛИО и оплаты: [orders-roles-payments.md](references/orders-roles-payments.md).
4. Для таблиц, процедур или записи в ФОЛИО дополнительно используй `$work-with-folio-mssql` и начни с его `references/source-map.md`.
5. Для кабинета, API и операторских действий Checkbox используй `$checkbox-ua`; для цепочки WayForPay → Checkbox дополнительно используй `$checkbox-wayforpay-woo`.

## Непереговорные правила

- Не правь WooCommerce, GeneratePress или сторонний плагин напрямую, если поведение можно реализовать в собственном plugin/MU-plugin.
- При HPOS работай с заказами через WooCommerce CRUD (`wc_get_order()`, методы `WC_Order`, `save()`), а не прямой записью в `wp_posts`/`wp_postmeta`.
- Не смешивай транзакции MariaDB/WordPress и ФОЛИО/MSSQL. Связь с ФОЛИО выполняй через Java API и WordPress proxy по документированному контракту.
- В товарной аналитике не выводи направление, спрос и оплату из одного
  `VID_DOC`: `*РАЗОВАЯ` исключается только из планирования закупки, а
  предоплата/отсрочка не изменяют движение. PHP читает готовую классификацию
  Java/MariaDB и не повторяет её своими условиями.
- Любую массовую синхронизацию запускай через общий ecosystem lock. Не создавай второй независимый lock для соседнего процесса.
- Сначала preview, затем отдельное подтверждение apply для финансовых, документных и медиа-операций. Не повторяй мутирующий запрос автоматически после тайм-аута или неизвестного результата.
- Все новые пользовательские и менеджерские строки пиши на английском как `msgid` с text domain владельца и обновляй украинский/русский перевод. Не встраивай украинский текст прямо в бизнес-код.
- Не хардкодь локальные ID страниц, пользователей, терминов складов или документов. Получай страницы из Woo options, склады из taxonomy/meta и связи ФОЛИО из meta/API.
- Не публикуй в коде, skill, документации или ответе токены, пароли, банковские реквизиты, персональные данные клиентов, строки соединения и внутренние адреса.
- Не меняй существующие пользовательские изменения в грязном worktree. Проверяй `git status` до и после работы.

## Режимы работы

### Диагностика

Работай read-only. Сверяй UI, PHP/JS, Woo settings, таблицы и ответ Java. Разделяй: **подтверждено**, **вывод**, **нужно проверить**.

### Изменение кода

Сохраняй текущие ownership boundaries и i18n. После изменения выполняй точечный lint/test, затем проверку пользовательского сценария. Для UI проверяй desktop и mobile, ошибки AJAX и видимое состояние ожидания.

Если создаёшь новый собственный plugin, в той же задаче выполни lifecycle из `deployment-and-configuration.md`: Git allow-list, `deploy_plugins.list`, i18n, локальная активация/миграция, deploy dry-run, явная политика production activation и rollback. Не называй плагин готовым к production, пока незавершённые пункты не перечислены явно.

### Операторская операция

Давай пошаговую инструкцию с предварительными условиями, preview, критериями допуска к apply, ожидаемым результатом и безопасным восстановлением. Не считай открытие административной страницы разрешением на запись.

### Производственная запись

Требуй явного решения пользователя для самой записи. Перед запуском проверяй backup/maintenance window, общий lock, состояние фоновой задачи и способ определить неизвестный итог.

## Постоянное пополнение skill

Когда в задаче подтверждено новое устойчивое знание о проекте или исправлено старое:

1. Без отдельного напоминания пользователя обнови в той же задаче один подходящий файл в `references/`, если новое знание меняет будущие действия в этом skill.
2. Укажи источник: код, Woo setting, схема, API-документ или воспроизводимая проверка; для изменчивого факта добавь дату проверки.
3. Замени устаревшее утверждение, а не добавляй рядом противоречащую заметку.
4. Гипотезу помечай как `Нужно проверить`; не превращай единичный сбой в общее правило.
5. Не копируй сырые логи и приватные данные. Сохраняй только обезличенный инвариант и путь к источнику.
6. После обновления запускай validator skill и проверку ссылок.

## Завершение задачи

Сообщи владельца изменённого поведения, затронутые файлы, проверку, необходимость активации/настройки и остаточный риск. Для нового плагина отдельно укажи: отслеживается ли он Git, включён ли в deploy manifest, активирован ли локально/на production и какие секреты/options ещё не настроены. Для изменений кода или документации всегда предложи краткое название коммита.
