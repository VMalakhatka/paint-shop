# Checkbox API и WooCommerce

## Выбор поверхности

- Официальный API — для повторяемых операций, интеграций, сверки и автоматизации.
- Портал — для регистрации, настроек организации, функций без API и визуальной проверки.
- WooCommerce — владелец заказа, клиента, строк и статуса оплаты; Checkbox — владелец фискального чека, смены и статуса ДПС.

Не автоматизируй UI вместо доступного официального API. Не вызывай недокументированные внутренние endpoints портала.

## Перед разработкой

1. Открой текущий Redoc: https://api.checkbox.ua/api/redoc и release notes: https://wiki.checkbox.ua/update.
2. Выяви доступные tags/операции для авторизации, кассиров, касс, смен, чеков, возвратов, служебных операций, отчётов и справочников. Не полагайся на сохранённые пути и поля.
3. Зафиксируй base URL, версию, auth-схему, scopes/роль, request/response schema, обязательные поля, pagination, rate limits, idempotency/external ID и поведение ошибок.
4. Проверь test/live, организацию, кассу, кассира/печать и открытую смену.
5. Определи, какая система владеет открытием/закрытием смены и повторными попытками.

## Секреты

- Не проси пользователя вставлять секреты в чат.
- Храни токены и PIN в deployment-managed secrets или защищённых константах вне Git.
- Не сохраняй КЭП и его пароль в WordPress, заказе или логах.
- Редактируй Authorization, licence key, PIN, email, телефон, IP и URL чека в диагностике.
- Не создавай новый ключ, если существующий можно безопасно использовать; создание/ротация требует подтверждения.

## Надёжность

- Дай каждой операции стабильный ключ: организация/касса + внешний заказ + тип операции + refund ID для возврата.
- Защити ключ database-level unique constraint или эквивалентной атомарной блокировкой.
- До каждого внешнего вызова проверяй локальное состояние и Checkbox.
- На транспортный timeout ставь статус `uncertain`, затем выполняй reconciliation; не отправляй второй чек вслепую.
- Автоматически повторяй только временные ошибки с ограниченным backoff. Ошибки данных/налогов требуют исправления и ручного решения.
- Сохраняй безопасный audit trail: operation key, external payment/order ID, receipt/shift ID, fiscal number, timestamps, payload hash, status, attempts и очищенную ошибку.

## WooCommerce

Для KREUL размещай интеграцию в отдельном собственном плагине, например `pc-checkbox-fiscalization`. Не патчь WooCommerce, WayForPay или сторонний Checkbox-плагин; не добавляй фискализацию в Java/ФОЛИО.

- С заказами работай через WooCommerce CRUD и HPOS-compatible hooks.
- Подтверждённый платёж запускает одну асинхронную sale-операцию через Action Scheduler.
- Состояние операции хранится в отдельном transactional store; order meta содержит только менеджерское представление.
- Сумма фискального чека обязана равняться фактически полученной сумме.
- Доставка, скидка, округление, переменные товары, дробное количество, налоговая группа и единица имеют детерминированный mapping.
- Полный/частичный возврат запускается только после подтверждённого денежного возврата и имеет отдельный ключ.
- В admin показывай статус, фискальный номер, ссылку, очищенную ошибку и безопасное действие reconciliation/retry.
- Добавь dry-run, kill switch новых операций и отдельный переключатель автоматических возвратов.

Для WayForPay применяй инварианты `$checkbox-wayforpay-woo`: валидированный callback и transaction ID, один провайдер фискализации, защита от дублей и независимость ФОЛИО. Для Nova Poshta наложенного платежа не используй событие WayForPay; владелец момента фискализации определяется отдельным процессом доставки/оплаты.

## Проверка

Минимально проверь:

- успешную и отклонённую оплату;
- повторный callback/hook;
- callback до и после возврата браузера;
- временный сбой и неизвестный outcome;
- скидки, доставку, округление и равенство итога;
- закрытую/длительную смену и просроченный КЭП;
- полный и частичный возврат, повтор возврата и запрет over-refund;
- HPOS и фактический checkout flow;
- один downstream-документ ФОЛИО после оплаты;
- отсутствие второго чека от WayForPay pRRO;
- видимость статуса менеджеру и отсутствие секретов в логах.

Production-ключи и низкостоимостный боевой чек используй только после локальной/staging проверки и отдельного разрешения. После запуска сверь чек в Checkbox и статус ДПС, затем проверь контролируемый возврат.
