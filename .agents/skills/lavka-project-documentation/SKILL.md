# Lavka Project Documentation

Поддерживай документацию проекта как проверяемую часть продукта. Этот skill владеет
структурой, маршрутизацией, актуальностью и контролем документов, но не подменяет
владельцев WordPress, Java, ФОЛИО, инфраструктуры и внешних сервисов.

## Начало работы

1. Прочитай [карту документации](../../../docs/README.md) и
   [политику актуализации](../../../docs/DOCUMENTATION_POLICY.md).
2. Когда нужно выбрать основной документ или провести ревизию, прочитай
   [document-map.md](references/document-map.md).
3. Определи владельца изменившегося факта и используй его профильный skill:
   `$lavka-woo`, `$build-java-docker-runtime`, `$work-with-folio-mssql`,
   `$server-lavka`, `$manage-ovh-infrastructure`, `$image-in-woo` или другой
   доменный skill.
4. Подтверди факт по текущему коду, конфигурации без значений секретов, API-контракту
   или воспроизводимой read-only проверке. Старый документ не подтверждает сам себя.

## Режимы

### Изменение проекта

Определи documentation impact до завершения задачи. Обнови один основной документ
в том же diff; соседние документы должны ссылаться на него, а не копировать длинный
workflow. Если изменились будущие решения Codex, отдельно обнови профильный skill.

Если изменение видно оптовому клиенту или меняет его путь, обязательно используй
оптовый publication workflow из `docs/DOCUMENTATION_POLICY.md`. Обнови
`docs/WHOLESALE_CUSTOMER_GUIDE_UK.md`, затем вместе с `$lavka-woo` синхронизируй
опубликованную справку **«Як замовляти»** в `pc-wholesale-help`, её переводы,
контекстные ссылки и затронутые скриншоты. В завершении раздельно сообщи, обновлён
ли канон, обновлён ли код справки и проверена ли production-страница. Изменение
Markdown само по себе не означает, что инструкция уже опубликована на сайте.

### Создание или реорганизация документации

Сначала выбери аудиторию и владельца факта. Создавай новый документ только когда у
него есть отдельная задача и жизненный цикл. Обнови `docs/README.md`, карту skill и
проверку обязательных входных файлов, если новый документ становится поддерживаемым
регламентом.

Для сквозной backend-документации используй `docs/BACKEND_GUIDE.md`: он связывает
PHP, Java, базы, окружения и development workflow, но направляет точные payload,
runtime-команды и operator steps в документы их владельцев.

### Ревизия

Проверяй источники, дату, владельца, дубли, противоречия, broken links, секреты,
unknown outcome, rollback и закрытые gaps. Результат разделяй на `Подтверждено`,
`Вывод`, `Нужно проверить` и `План`.

## Непереговорные правила

- Один устойчивый факт имеет одно каноническое место. Исправляй старый текст, а не
  добавляй рядом противоречащую заметку.
- Human runbook описывает действие, результат, ошибку и rollback; skill хранит
  routing/invariants; API-документ хранит точный contract; roadmap не выдаётся за
  реализованное поведение.
- Не переносить в docs, examples, skills или отчёт значения secrets, connection
  strings, internal addresses, customer payloads и raw logs.
- Изменчивый факт получает источник, окружение и `Проверено: YYYY-MM-DD`.
- HTTP 200, запущенный process или наличие файла не являются достаточным
  доказательством бизнес-результата.
- Документирование production-write не разрешает саму операцию. Preview, approval,
  idempotency, unknown outcome и stopping condition сохраняют правила владельца.
- WordPress CI не видит Java diff, а Java CI не видит WordPress runbook. Для
  cross-repository изменения обнови документы обоих владельцев; локальные gates не
  заменяют review этой связи.

## Проверка

Из корня проекта запускай:

```bash
python3 .agents/skills/lavka-project-documentation/scripts/check-documentation.py
python3 .agents/skills/lavka-project-documentation/scripts/check-documentation.py --working-tree
```

Pre-commit использует `--staged`, pull-request CI — `--base`. Проверка доказывает
наличие связанного документа и исправность относительных ссылок, но не смысловую
правильность. После неё вручную сверяй команды, статусы, safe defaults, rollback и
дату с источником.

## Завершение

Сообщи основной обновлённый документ, источник подтверждения, выполненные проверки,
оставшиеся gaps и нужен ли administrative action для hook/CI/protected branch.
Всегда предложи короткое название коммита.
